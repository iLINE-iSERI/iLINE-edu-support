## ⭐ 최우선 목표 (고정)

> **창의재단 교원양성지원사업 사이트가 정상 작동하게 만드는 것이 1순위다.**
> 다른 작업은 이 목표를 밀어내지 않는 선에서만 진행한다.

| 순위 | 대상 | 근거 |
|---|---|---|
| **1** | **창의재단 사이트 구축** (`support.iline.or.kr`) | 사업 공고 일정에 묶여 있어 늦출 수 없음 |
| 2 | 인트로 허브 | 창의재단이 서기 전까지는 연결할 대상이 없음 |
| 3 | iLINE 루트 교체 · 리다이렉트 | 인트로 확정 이후 |
| 4 | 디자인 다듬기 | 기능 동작 이후 |

**작업 배분 원칙**
- 창의재단이 블로킹(H-1 폼 명세 대기 등)일 때만 2·3순위로 이동한다
- 디자인 논의가 길어지면 기능 구현으로 되돌린다
- 새 요구사항이 들어오면 위 순위에 비추어 배치하고, 1순위를 밀어낼 경우 그 사실을 먼저 알린다

## 1. 확정 사항 ① — UI 구조: A″안 (인트로 허브 + 서브도메인)

### 1-1. K-Startup 실측 구조

참고 대상을 실제로 확인했습니다.

**창업진흥원 최상위** — 3개 서비스 카드로 분기
```
모두의 창업  │  K-Startup  │  스타트업 원스톱 지원센터
```

**K-Startup 내부 GNB** — 4개 대메뉴 + 우상단 계정 영역
```
사업소개 │ 사업공고 │ 알림마당 │ 고객센터        [로그인] [회원가입] [마이페이지▾]
  ├사업화  ├모집중   ├공지사항    ├FAQ
  ├R&D     └모집마감  ├카드뉴스    ├상담하기
  ├시설·공간         ├창업정보     ├온라인 매뉴얼
  ├멘토링·교육       │ (성공사례)  ├신고센터
  └글로벌 등          └생태계      └자료실
```

> 📌 **주목할 점 3가지**
> 1. 최상위는 **카드 분기**, 각 서비스 내부는 **독립 GNB** — A′안 그대로입니다.
> 2. 대메뉴가 **4개뿐**입니다. 사업안내 / 공고 / 알림 / 고객센터. 나머지는 전부 2뎁스로 내렸습니다.
> 3. **"갤러리"라는 메뉴가 없습니다.** 성공사례·카드뉴스는 `알림마당` 하위 게시판으로 흡수되어 있습니다. → §3의 갤러리 논의에 직접적인 시사점입니다.

### 1-2. 확정 아키텍처 — A″안 (D-1 개정 / D-20)

> **v0.14 개정 사유**: 창의재단을 **별도 레포**로 가기로 하면서 "한 앱 안에서 `/great/*`·`/support/*`로 나눈다"는 A′안의 전제가 깨졌습니다. 레포 실측과 Vercel 요금 구조를 확인해 아래로 개정합니다.

#### 도메인·프로젝트 배치

```
iline.or.kr              → 인트로 허브        ┐ iLINE 레포 (기존)
iline.or.kr/home         → iLINE 랜딩        │ = Vercel 프로젝트 ①
iline.or.kr/courses …    → iLINE 기존 경로   ┘   전부 URL 보존
support.iline.or.kr      → 창의재단           = 별도 레포 · Vercel 프로젝트 ②
```

#### 왜 이 배치인가

**① 한 도메인에 여러 프로젝트를 경로로 나누는 건 유료입니다**

Vercel은 **프로덕션 도메인 하나 = 프로젝트 하나**가 원칙이고, 경로로 나누려면 Microfrontends 기능이 필요합니다. 그런데 **Hobby·Pro 모두 프로젝트 2개까지만 포함**이고 **세 번째부터 프로젝트당 월 $250**입니다.

| | Hobby | Pro |
|---|---|---|
| 포함 프로젝트 | 2개 | 2개 |
| 추가 프로젝트 | 불가 | **$250/월** |

→ 인트로를 **별도 프로젝트로 만들면 3개**가 되어 과금 대상입니다. **인트로를 iLINE 레포에 두면 2개**로 무과금 한도 안에 들어옵니다.

**② iLINE URL이 전부 보존됩니다**

A′안대로 `/great/*`로 옮겼다면 33개 라우트에 301 리다이렉트를 걸어야 했습니다. 인트로만 루트에 넣으면 **리다이렉트 대상이 루트 한 페이지뿐**입니다. v0.3~0.13에서 "A′안의 필수 부수 작업"으로 잡아둔 대규모 리다이렉트 작업이 사라집니다.

**③ 창의재단은 완전히 독립합니다**

별도 레포 · 별도 배포 · 별도 환경변수 · 별도 서브도메인. 한쪽 배포가 다른 쪽을 깨뜨릴 수 없고, **계정 분리(D-6)와도 자연스럽게 맞습니다**(쿠키·세션이 도메인 단위로 원래 분리됨). 사업 종료 시 프로젝트 하나만 내리면 됩니다.

### 2-2. 계정 모델 — 서비스별 분리 운영 (Q-1 해소 → D-6)

> **결정**: iLINE과 창의재단 계정을 **각각 운영**한다. 통합 여부는 현 시점에서 판단하지 않고 보류한다.

#### 참고: 통합을 검토했던 근거 (기록용)

| 방향 | 가능성 |
|---|---|
| iLINE → 창의재단 | 거의 없음 |
| **창의재단 → iLINE** | **충분히 있음** — 사업 참여 교원이 AI 강의 수강 |

겹침이 단방향으로 존재하므로 통합 이점이 있으나, **지금 확정할 근거가 부족하다는 판단에 따라 분리로 시작**합니다. 아래는 그 판단이 나중에 바뀔 수 있다는 전제 하에, **되돌리는 비용을 최소화하는 방법**입니다.

#### ⚠️ 구현 방식 선택 — 여기서 갈립니다

"계정을 각각 운영한다"를 코드로 옮기는 방법이 두 가지이고, **나중에 통합할 때의 비용이 완전히 다릅니다.**

**S1. Firebase 프로젝트를 2개로 분리**

- 진짜 완전 분리. 인프라·콘솔·요금까지 별개
- ❌ **나중에 통합이 사실상 불가능합니다.** Auth 사용자를 다른 프로젝트로 옮기려면 비밀번호 해시를 통째로 이관해야 하고, **구글 로그인 사용자는 프로젝트가 다르면 uid 자체가 달라져** 자동 연결이 안 됩니다. 전원 재가입 외에 방법이 없습니다
- 운영 부담 2배 (환경변수, 배포, 요금, 모니터링 전부 이중)

**S2. 같은 Firebase 프로젝트 안에서 서비스별로 분리** ⭐ **권장**

- 사용자 경험은 동일합니다 — 창의재단을 이용하려면 **별도 회원 등록 절차**를 거칩니다 (실명·소속·연락처·개인정보 동의)
- 데이터도 완전 분리 (`support_*` 컬렉션, `/support/{uid}/` Storage 경로, 별도 Rules)
- ✅ **나중에 통합 결정이 나면 화면과 동의 로직만 바꾸면 끝납니다.** 데이터 이관 없음
- 지금 지불하는 추가 비용: **사실상 없음**

> **권고: S2입니다.** 판단을 보류하신 것이라면, 되돌릴 수 없는 선택(S1)보다 되돌릴 수 있는 선택(S2)을 하는 게 맞습니다. 분리 운영이라는 결정은 그대로 지키면서, 나중에 방향이 바뀌었을 때의 문이 닫히지 않습니다.

**✅ 확정 (D-23)**: **인증 신원은 하나, 서비스별 회원 등록이 그 위에 얹히는 구조**로 갑니다. 같은 구글 계정으로 양쪽을 쓰면 Auth uid는 동일하고, 창의재단을 이용하려면 **별도 회원 등록 절차**(실명·소속·연락처·개인정보 동의)를 거칩니다. 기술적으로 완전히 별개인 두 계정(S1)은 채택하지 않습니다.

구체적 동작 *(⚠️ 아래 표는 D-25로 개정되었습니다 — §2-2′ 및 D-27 참조)*:

| 상황 | 결과 |
|---|---|
| ~~iLINE 회원이 창의재단에 처음 접속~~ | ~~로그인은 되지만 **창의재단 회원이 아님** → 회원 등록 화면으로 유도~~ |
| 등록 완료 후 | `support_users/{uid}` 문서 생성. 이때부터 창의재단 이용 가능 |
| ~~창의재단만 쓰던 사람이 iLINE 접속~~ | ~~iLINE 쪽 회원 데이터가 없으면 iLINE 기준으로 신규 가입 처리~~ |
| 한쪽 탈퇴 | 그쪽 서비스 회원 문서만 비활성화. 삭제하지 않는다(보존 의무) |

### 2-2′. Firebase 프로젝트 분리 (D-25) — 09-05 개정

> ⚠️ **위 §2-2의 "같은 Firebase 프로젝트" 전제(D-8)는 폐기되었습니다.**
> 회원 판별 로직(D-23의 판별 기준)은 **그대로 유효**합니다. 바뀐 것은 그 데이터가 **어느 프로젝트에 있는가** 뿐입니다.

**분리한 이유 — 프로젝트 단위로만 나눌 수 있는 것들**

| | 같은 프로젝트일 때 | 분리했을 때 |
|---|---|---|
| **보안 규칙** | 파일이 한 장. 지원사업 규칙을 고칠 때마다 운영 중인 iLINE이 인질이 됨 | 서로 무관. 규칙 사고의 폭발 반경이 0 |
| **콘솔 권한** | Firestore 접근권을 주면 **iLINE 데이터까지 보임**. 사업 담당자만 격리 불가 | "지원사업만 보는 관리자"를 만들 수 있음 |
| **파기 증명** | 문서를 골라 지우고 지웠음을 입증해야 함 | **프로젝트 삭제 = 파기 완료** |
| **할당량·요금** | 한쪽 사고가 다른 쪽 서비스에 전이 | 격리 |

재단 사업은 **감사와 이관이 전제**입니다. 두 번째 행이 결정적이었습니다.

**대가로 잃은 것**

1. **인증 신원이 갈립니다.** D-23이 그리던 "iLINE 계정으로 와서 회원 등록만 얹기"는 불가능해졌습니다. Google 로그인은 같은 구글 계정을 고르면 되므로 체감 마찰이 작지만, 이메일·비밀번호 가입자는 새로 만들어야 합니다. → FAQ 문구 수정 완료.
2. **Blaze(종량제) 요금제가 필요합니다.** 2024-09 이후 생성 프로젝트는 Storage 기본 버킷 생성 시 결제 계정 연결이 필수입니다. 무료 할당량은 유지되므로 실 청구액은 0원에 가깝지만, **예산 알림 설정을 필수 절차로 못박았습니다**(`docs/06-new-firebase-project.md` §2).

**되돌릴 수 있게 남긴 것**

컬렉션 접두어 `support_` 와 Storage 루트 `support/` 를 **그대로 유지**합니다. 프로젝트가 갈렸으니 기능상 불필요하지만, 다시 합쳐야 할 상황이 와도 **이름 충돌 없이 그대로 이식**됩니다. 분리를 편도 결정으로 만들지 않기 위한 장치입니다.

**전환 시점을 지금으로 잡은 근거**: 실제 학생 개인정보가 아직 한 건도 들어가지 않았습니다. 지금은 환경변수 교체 수준(반나절)이지만, 실데이터 이후에는 개인정보 이관 작업이 됩니다.

#### D-27 — 계정 완전 분리 확정 (09-05)

Firebase는 **회원 명부(Authentication)가 프로젝트에 종속**됩니다. 데이터·규칙만 나누고 명부는 공유하는 설정은 존재하지 않습니다. 따라서 D-25는 계정 분리를 필연적으로 동반합니다.

**이를 명시적으로 수용합니다.** D-23이 전제하던 "인증 신원 1개"는 폐기합니다.

| | 잃는 것 | 실제 크기 |
|---|---|---|
| Google 로그인 | 계정 선택을 한 번 더 | 같은 구글 계정을 고르면 끝 |
| 이메일 로그인 | 비밀번호를 새로 설정 | 같은 값으로 정해도 무방 |
| 회원 정보 입력 | — | D-23에서도 어차피 받았음. **차이 없음** |

**검토했으나 채택하지 않은 우회로**: 커스텀 토큰으로 명부를 연결하는 방식. 양쪽에 서버와 서비스 계정 키가 생기고(현재는 서버리스), 그 키가 유출되면 임의 계정 로그인이 가능해지며, 무엇보다 **두 서비스를 다시 붙이는 셈이라 D-25의 격리 근거를 스스로 무너뜨립니다.**

**코드 영향**: 없습니다. 접근 판별을 처음부터 "회원 문서 존재 여부"로 짜두었기 때문에(D-23 본체), 계정이 갈려도 로직이 그대로 성립합니다. 전제를 서술한 주석과 FAQ 문구만 수정했습니다.

#### 분리 운영에서도 그대로 적용되는 원칙

**① 개인정보 동의는 목적별로 받고 이력을 남긴다**
창의재단 가입 시 신분증·정산 정보 수집 동의를 별도로 받고, `consents[]`에 목적·일시·약관 버전을 기록합니다. 감사 시 가장 먼저 확인되는 지점입니다.

**② "탈퇴"는 계정 삭제가 아니라 비활성화여야 한다**
창의재단 신청·정산 이력은 국고사업 **보존 의무** 대상입니다. 탈퇴 요청이 와도 서류가 사라지면 안 되므로, 탈퇴 = 로그인 차단 + 개인정보 마스킹 + 서류 보존으로 설계합니다.

**③ 권한은 서비스 스코프로 준다**

```js
{ roles: { support: 'applicant' } }   // ✅
{ admin: true }                        // ❌ 서비스 경계를 넘음
```

### 2-3. 운영 모델 — 관리자 화면 없이 구글 스프레드시트로 (Q-2 해소 → D-7)

> **결정**: 관리자 백오피스를 만들지 않는다. 신청자용 화면 위주로 개발하고, 신청 내용은 **구글 스프레드시트로 관리**한다.

**범위가 크게 줄어듭니다.** 기존 Phase 5(관리자 백오피스 5~7일)가 **스프레드시트 연동 2~3일**로 대체됩니다. 담당자가 익숙한 도구로 정렬·필터·심사를 할 수 있다는 점도 실용적입니다.

다만 **스프레드시트가 대신해 줄 수 없는 것**이 있어, 아래는 별도 설계가 필요합니다.

#### ① 동기화 방향을 먼저 정해야 합니다 (Q-5)

| 안 | 구조 | 평가 |
|---|---|---|
| **W1. 단방향** (Firestore → Sheets) | 제출 시 시트에 자동 추가. 심사·선정은 시트에서 하고 **결과는 이메일·공문으로 개별 통보** | ⭐ **권장.** 단순하고 깨질 데가 없음 |
| **W2. 양방향** (시트의 상태 열 → 사이트 반영) | 담당자가 시트에 `선정/반려` 입력 → 신청자 화면에 표시 | ⚠️ **비권장.** 셀 하나 잘못 건드리면 신청자 화면이 깨짐. 권한 통제·감사 로그 불가 |
| **W3. 단방향 + 최소 화면 1장** | 시트로 관리하되 **상태 변경 전용 화면 1개**만 제작 | W2가 필요해질 때의 대안 (+2~3일) |

> ✅ **확정: W3** (D-10). 신청자가 마이페이지에서 신청 현황·결과를 확인하므로 상태를 바꿀 수단이 필요하고, 그 수단은 시트가 아니라 **화면**이어야 합니다.
>
> **담당자 화면(`/support/staff`)에 들어갈 것 — 딱 이만큼만**
> - 신청 목록 (연도·상태 필터, 검색)
> - 상태 변경 드롭다운 + **보완요청·미선정 사유 입력**
> - 정산 승인 / 반려 (Phase 6)
>
> 목록·필터·정렬·엑셀 내보내기 같은 **조회·분석 기능은 넣지 않습니다** — 그건 시트가 훨씬 잘합니다. 이 화면은 **"쓰기 전용"**으로 좁게 유지하는 것이 D-7의 취지를 지키는 방법입니다.
>
> ⚠️ 상태를 화면에서 바꾸므로 **Firestore가 상태의 원본**이고, 시트의 상태 열은 **참고용 사본**입니다. 담당자가 시트에서 상태를 고쳐도 사이트에 반영되지 않는다는 점을 운영 매뉴얼에 명시해야 합니다 (가장 흔한 혼선 지점).
> 실소요: **+3~4일** (정산 승인/반려 포함)

#### ② 동기화 구현 방식

```
신청자 제출 → Firestore 저장 → Vercel Route Handler
                                 └→ Google Sheets API (서비스 계정) → 시트에 행 추가
```

- **Vercel Route Handler + 구글 서비스 계정** 방식을 권장합니다. Firebase Cloud Functions로 외부 API를 호출하려면 **Blaze(종량제) 요금제 전환이 필요**하지만, Vercel 경유는 그럴 필요가 없습니다
- 동기화 실패에 대비해 **Firestore를 원본(source of truth)으로 유지**하고 시트는 사본으로 취급합니다
- **재동기화(수동 트리거)** 수단을 하나 만들어 둡니다 — 시트가 꼬였을 때 원본에서 다시 그릴 수 있어야 합니다

#### ③ 첨부파일 — 구글 공유 드라이브 연동 (Q-6 해소 → D-9)

**결론부터: 가능하고, 이게 가장 나은 방식입니다.** 시트 셀에 드라이브 링크를 넣고 담당자가 클릭하면 바로 열리는 구조를 만들 수 있습니다.

##### 왜 "공유 드라이브"여야 하는가 (개인 드라이브로는 안 됩니다)

구글 **서비스 계정**(서버가 API를 호출할 때 쓰는 자동화 계정)에는 **자체 저장 용량이 없습니다.** 서비스 계정이 개인 드라이브(My Drive)에 파일을 만들려고 하면 용량 초과로 실패하거나, 소유권이 애매해져서 나중에 아무도 관리할 수 없는 파일이 생깁니다. 실제로 이 방식으로 만들었다가 막히는 사례가 흔합니다.

**공유 드라이브는 파일 소유자가 개인이 아니라 드라이브(조직) 자체**입니다. 서비스 계정을 공유 드라이브 멤버(콘텐츠 관리자)로 추가하면 조직 용량을 사용하므로 이 문제가 사라지고, **담당자가 바뀌어도 파일이 그대로 남습니다.** 국고사업처럼 인수인계와 보존이 중요한 경우에 특히 맞습니다.

> 참고로 공유 드라이브는 과거 상위 요금제 전용이었으나 2024년부터 Business Starter를 포함한 대부분의 Workspace 에디션에서 사용 가능합니다. 다만 **개인 gmail 계정으로는 공유 드라이브를 만들 수 없습니다** → **Q-9 확인 필요.**

##### 확정 구조

```
신청자 업로드
   → Firebase Storage 저장            ← 원본(source of truth), 우리 통제 하
   → Vercel Route Handler
        → Google Drive API (서비스 계정, supportsAllDrives: true)
             → 공유 드라이브에 사본 업로드
        → 반환된 webViewLink를 시트 셀에 기록
```

**Storage 원본 + Drive 사본, 이중 보관을 권합니다.**
- 신청자 업로드는 Storage로 빠르게 끝내고, 드라이브 전송은 서버에서 처리 → 드라이브 API 장애가 신청자 화면에 노출되지 않습니다
- 시트·드라이브가 꼬여도 **원본에서 다시 만들 수 있습니다**
- 서류 파일은 용량이 작아 이중 보관 비용이 무의미한 수준입니다

##### 드라이브 폴더 구조 (제안)

```
[공유 드라이브] 2026 교원양성지원사업
├─ 01_과제신청/
│   ├─ 20260901_홍길동_A20260001/
│   │   ├─ 신분증.jpg
│   │   ├─ 재직증명서.pdf
│   │   └─ 신청서.pdf            ← 제출 시 자동 생성 (§2-3 ④)
│   └─ ...
└─ 02_정산/
    └─ 20261120_홍길동_A20260001/
        ├─ 영수증_01.jpg
        └─ ...
```

**시트에는 파일별 링크를 여러 열에 나열하지 말고, 신청건별 폴더 링크 1개**를 넣는 것을 권합니다. 열이 깔끔해지고, 서류가 추가돼도 시트 구조를 바꿀 필요가 없습니다.

| 신청번호 | 성명 | 소속 | … | 첨부서류 |
|---|---|---|---|---|
| A20260001 | 홍길동 | ○○초 | … | [📁 폴더 열기](#) |

##### 담당자 권한 = 공유 드라이브 멤버십

파일마다 권한을 따로 설정할 필요가 없습니다. **담당자를 공유 드라이브 멤버로 추가하면 시트의 링크가 그대로 열립니다.** 즉 접근 통제가 곧 멤버 관리이므로:

- 멤버 추가·제거 절차를 문서화하고, **인수인계·퇴사 시 즉시 제거**
- 외부 공유(링크가 있는 모든 사용자)는 **관리 콘솔에서 차단**
- 멤버 역할은 '콘텐츠 관리자' 이하로 — '관리자'를 남발하면 폴더 구조가 훼손됩니다

##### D-9의 효과

- ✅ **F3(별도 파일 열람 화면) 불필요** → 개발 1~2일 절감
- ✅ 담당자는 익숙한 드라이브 UI에서 미리보기·다운로드
- ✅ 사업 종료 후 폴더째 아카이빙·이관이 쉬움
- ⚠️ **개인정보 반출 범위가 커집니다** — 기존엔 시트에 텍스트만 나갔지만 이제 **신분증 이미지까지** 드라이브로 나갑니다. **Q-7 행정 확인의 중요도가 올라갔습니다**
- ⚠️ 파기 절차가 **Storage와 Drive 두 곳**이 됩니다. 보존기간 만료 시 양쪽 삭제 절차를 매뉴얼에 명시해야 합니다

##### Q-9이 "불가"(Workspace 없음)일 경우 대안

| 대안 | 방식 |
|---|---|
| A | 연구소 명의 **Workspace 신규 도입** (가장 깔끔) |
| B | **F3 원안 복귀** — 파일 열람 전용 화면 1장 자체 제작 (+1~2일) |
| C | 서명 URL을 시트에 기록 — 만료 문제로 **비권장** |

#### ④ 신청서 출력 동선이 바뀝니다 (Q-3 재점화)

기존 요구사항은 "**관리자가** 출력할 수 있는 형태"였는데 관리자 화면이 없어졌으므로 출력 주체를 다시 정해야 합니다. 스프레드시트 인쇄로는 신청서 서식이 나오지 않습니다.

- **제안**: 제출 시점에 **신청서 PDF를 자동 생성**해 Storage 원본 + **공유 드라이브 신청건 폴더**에 함께 넣습니다(§2-3 ③). 담당자는 드라이브에서 바로 열어 출력하고, 신청자도 마이페이지에서 본인 신청서를 인쇄·저장할 수 있게 합니다
- 이 방식이면 서식이 정확히 보존되고 사후 감사에도 원본이 남습니다

#### ⑤ 개인정보 반출 검토 필요 (Q-7)

신청 데이터에는 실명·연락처·소속이 들어가고 첨부에는 신분증이 있습니다. 이를 **외부 서비스인 구글 스프레드시트로 내보내는 것**이 기관 개인정보 처리방침상 가능한지 확인이 필요합니다. 실무적으로는:

- 시트 **공유 설정을 링크 공유 금지 + 지정 계정만**으로 강제 (가장 흔한 사고 지점입니다)
- 시트에는 **최소 항목만** 반출하고, 첨부 실물은 시트가 아니라 **공유 드라이브에서 권한으로 통제** (§2-3 ③)
- 공유 드라이브 **외부 공유 차단** + 멤버 최소화 — D-9로 신분증 이미지까지 나가므로 이 통제가 핵심입니다
- 처리방침에 위탁·제3자 제공 내용 반영 여부 확인

> 이 항목은 개발 이슈가 아니라 **행정 확인 사항**입니다. 담당 교수님·기관 행정과 확인 부탁드립니다.

### 2-4. 모바일 반응형 — 필수 요구사항 (D-24)

> **결정**: 모든 화면이 스마트폰에서 **완전히 동작**해야 한다. "보이기만" 하는 수준이 아니라 신청·업로드·정산까지 폰으로 끝낼 수 있어야 한다.

#### 왜 중요한가

교원은 학교에서 데스크톱을 쓰지만, **영수증 촬영·신분증 촬영은 사실상 폰으로 합니다.** 정산 증빙 업로드가 폰에서 안 되면 "PC로 옮겨서 다시" 하는 과정이 생기고, 이게 정산 기간 민원의 주된 원인이 됩니다.

#### 화면별 기준

| 화면 | 모바일에서 반드시 되어야 할 것 |
|---|---|
| 인트로 허브 | 카드 세로 스택, 터치 영역 충분 |
| 사업안내·알림마당 | 표·타임라인이 가로 스크롤 없이 읽힘 |
| **신청서 작성** | 다단계 폼이 한 화면에 한 단계씩. **임시저장**이 특히 중요 (폰은 이탈이 잦음) |
| **파일 첨부** | **카메라 직접 촬영 업로드** (`accept="image/*"` + `capture`), 업로드 진행률 표시 |
| **정산 증빙** | 영수증 여러 장 연속 촬영·추가, 항목별 금액 입력이 숫자 키패드로 |
| 마이페이지 | 상태 뱃지·반려 사유가 접히지 않고 보임 |
| 갤러리 | 카드 1열, 이미지 지연 로딩 |
| 담당자 화면 | 폰에서도 상태 변경 가능 (목록은 카드형으로 전환) |

#### 구현 규칙

- **모바일 우선(mobile-first)** 로 작성. 기본 스타일이 좁은 화면, `min-width` 미디어쿼리로 확장
- 브레이크포인트: `640 / 820 / 1024px`
- 터치 타깃 **최소 44×44px** (KWCAG·모바일 접근성)
- 표는 가로 스크롤 컨테이너로 감싸되, **본문이 가로로 밀리지 않게** 함
- 입력 필드에 적절한 `inputmode`·`autocomplete` 지정 (금액은 숫자 키패드)
- iOS 자동 확대 방지를 위해 입력 폰트 크기 **16px 이상**
- 긴 폼은 **자동 임시저장** (입력 중단·앱 전환 대비)

#### 검증

Phase 7 점검 항목에 **실제 스마트폰 실기기 테스트**를 포함합니다. 브라우저 개발자도구 시뮬레이터만으로는 파일 촬영 업로드·키패드 동작을 확인할 수 없습니다.

## 3. 확정 사항 ③ — 갤러리 채택 (H-2 해소 → D-12)

> **결정**: `갤러리(산출물)`를 **대메뉴로 채택**한다. 지도안·영상 등 산출물 중심.

v0.3에서 제안했던 "1차 오픈에서 빼고 나중에 판단" 방안 대신 **처음부터 대메뉴로 넣는 것**으로 확정되었습니다. 활동사진과 산출물을 나누지 않고 **산출물 중심 단일 메뉴**로 갑니다 (v0.2의 2분할안은 폐기).

### ⚠️ 다만 "빈 메뉴" 문제는 남아 있습니다

갤러리는 **선정자가 활동을 마쳐야 콘텐츠가 생깁니다.** 1차 오픈(신청 접수 시작) 시점에는 채울 산출물이 없습니다. 대메뉴 4개 중 하나가 비어 있으면 사이트 완성도가 떨어져 보입니다.

**대응안 (택1 또는 병행)**

| 안 | 방식 |
|---|---|
| **A** ⭐ | **이전 회차 산출물**이 있다면 그것으로 초기 콘텐츠 구성 (가장 자연스러움) |
| **B** | 오픈 시 메뉴는 노출하되 "첫 산출물은 ○○월 공개 예정" 안내 화면 |
| **C** | 1차 오픈에서는 메뉴 숨김 → 산출물 확보 후 노출 (코드는 미리 완성) |

→ **Q-12: 이전 회차 산출물(지도안 등)을 확보할 수 있습니까?** 있으면 A, 없으면 B를 권합니다.

### 기능 범위

- 목록: 카드 그리드 + **태그 필터 + 검색**
- 상세: 설명 + 첨부 다운로드
- 영상: **YouTube 비공개 임베드 권장** (Storage 직접 서빙은 트래픽 비용 급증)
- 공개 범위: **G-a·전체공개 여부 확인 필요** (§3-1 잔여 질문)

### 4-3. 제출 기능 배치 — M1 확정 (D-19)

> **결정**: 산출물 제출과 정산 증빙 제출을 **모두 마이페이지 하위**에 둔다. 갤러리는 **열람 전용**으로 유지한다.

```
[제출]  마이페이지 🔒          →  [승인]  담당자 화면 🔒  →  [열람]  갤러리 (공개)
  ├ 내 신청 현황                     ├ 신청 상태 변경          ├ 산출물
  ├ 산출물 제출                      ├ 정산 승인/반려          └ 활동사진
  ├ 정산 증빙 제출                   └ 갤러리 공개 승인
  ├ 제출 서류 보관함
  └ 회원정보 수정
```

**이 구조가 갖는 이점**

- **권한이 단순합니다.** 마이페이지 전체가 "본인 것만" 원칙 하나로 통제됩니다. 제출물이 갤러리 아래 있었다면 "같은 메뉴인데 어떤 건 공개, 어떤 건 본인만"이라는 예외를 만들어야 했습니다
- **정산 증빙(영수증·통장 사본)이 공개 성격의 메뉴에서 완전히 분리**됩니다. 개인정보 사고는 대개 이런 IA 혼동에서 납니다
- 이용자가 **"내가 제출한 것"을 한 화면에서** 봅니다 — 원래 의도하셨던 "제출물을 한군데 모으자"에 오히려 더 부합합니다
- 대메뉴 4개 구조가 그대로 유지됩니다

**노출 조건**

| 메뉴 | 표시 시점 |
|---|---|
| 내 신청 현황 | 로그인 시 항상 |
| **산출물 제출** | `선정(approved)` 이후 |
| **정산 증빙 제출** | `선정(approved)` + 정산 기간 개시 후 |
| 제출 서류 보관함 | 로그인 시 항상 |

> 미선정자나 정산 기간 전 이용자에게 빈 메뉴를 보여주지 않도록, **상태 기반으로 노출을 제어**합니다. 정산 기간이 열리면 마이페이지에 배지·알림을 띄워 유입시킵니다.

#### 갤러리 공개에는 승인 단계가 필요합니다

교원이 제출한 산출물이 **바로 갤러리에 공개되면 안 됩니다.** 학생 얼굴이 담긴 사진, 타 저작물 인용, 미완성 자료가 그대로 노출될 수 있습니다. 제출물에 `approved` 플래그를 두고 **담당자가 공개 승인한 것만** 갤러리에 노출합니다. → 담당자 화면(D-10)에 항목 하나 추가 (+1일).

→ **Q-15: 공개 여부는 담당자가 결정합니까, 제출자가 선택합니까?** (담당자 승인 권장)

### 4-4. 신청서 상태 흐름

```
작성중(draft) → 제출완료(submitted) → 검토중(reviewing)
                                       ├→ 선정(approved)  → 정산 기능 활성화
                                       ├→ 보완요청(revision) → 작성중으로 회귀
                                       └→ 미선정(rejected)
```

**마이페이지 상태 표시** (D-10으로 신청자에게 노출되므로 문구 확정 필요)

| 내부 status | 신청자 화면 표시 | 색상 |
|---|---|---|
| `draft` | 작성 중 | 회색 |
| `submitted` | 제출 완료 | 파랑 |
| `reviewing` | 검토 중 | 파랑 |
| `revision` | **보완 요청** + 사유 표시 | 주황 |
| `approved` | **선정** | 초록 |
| `rejected` | 미선정 | 회색 |

> Phase 0의 "사업 실제 진행 절차 인터뷰"에서 이 흐름과 문구가 실무와 맞는지 검증이 필요합니다. 특히 **보완요청 횟수 제한**과 **미선정 사유를 신청자에게 공개할지**가 결정되어야 합니다.

### 4-5. 개인/팀 신청 구조 (D-16 개정)

> **정정 (v0.11)**: v0.10은 "팀 = 대표자 1명이 대표로 신청"으로 잘못 전제했습니다.
> **팀 활동이어도 구성원이 각각 신청할 수 있다**는 점을 반영해 재작성합니다.

> **확정 요구사항**
> 1. 신청은 **개인·팀 둘 다 가능**
> 2. **여비 정산은 개인별**로 각각 진행
> 3. **산출물은 팀 단위**로 제출

#### ① 먼저 확인 — 팀 신청은 어떤 방식입니까? (Q-19 재정의)

| 모드 | 신청 | 정산 | 팀원 계정 |
|---|---|---|---|
| **모드 1. 대표 신청형** | 대표자 1명이 팀 대표로 1건 | 개인별 N건 | ❌ 없음 → 별도 부여 필요 |
| **모드 2. 각자 신청형** ⭐ | **구성원 각자 1건씩 (총 N건)** | 개인별 N건 (신청과 1:1) | ✅ **전원 보유** |
| **모드 3. 혼재** | 프로그램에 따라 다름 | | 둘 다 지원 필요 |

말씀하신 내용은 **모드 2**에 해당합니다.

#### ② 🎉 모드 2면 v0.10의 복잡한 설계가 대부분 사라집니다

v0.10에서 길게 논의했던 **T2 / T2+ (팀원 부분 계정, 초대 플로우, 권한 분기)가 통째로 불필요해집니다.**

> **구성원 각자가 신청한다 = 전원이 이미 계정을 가진 개인 신청자입니다.**
> 정산도 자기 신청건에 1:1로 붙으므로, 대표자가 남의 통장 사본을 취급할 일도 없고 초대 메일도 필요 없습니다.

| 항목 | v0.10 (모드 1 전제) | v0.11 (모드 2) |
|---|---|---|
| 팀원 계정 | 초대·간소가입 플로우 필요 | **불필요** — 각자 일반 가입 |
| 권한 분기 | 대표자/팀원 3역할 매트릭스 | **불필요** — 전원 동일 권한 |
| 정산 구조 | 신청 1건 : 정산 N건 | **신청 1건 : 정산 1건** (단순) |
| 개인정보 대리수집 | 이슈 있음 | **해소** |
| 작업량 | +8~12일 | **+2~3일** |

**약 6~9일이 절감됩니다.**

#### ③ 팀 표현 방식 — J1 확정 (D-17)

> **결정**: 신청건을 시스템적으로 묶지 않는다. **산출물 제출 폼에 `팀명`과 `구성원 이름` 입력란만** 둔다.

```
산출물 제출 폼
┌──────────────────────────────────────────┐
│ 활동 구분   ○ 개인   ● 팀                 │
│ 팀명        [ 제주AI수업연구회        ]   │
│ 구성원      [ 홍길동, 김철수, 이영희  ]   │
│ 제목        [ ...                     ]   │
│ 첨부        [ 파일 선택 ]                 │
└──────────────────────────────────────────┘
        ↓
갤러리 표기: 제주AI수업연구회 (홍길동, 김철수, 이영희)
```

- 신청·정산은 **전부 개인 단위**로 유지 — 팀 개념이 개입하지 않습니다
- 팀은 **산출물 제출 시점에만** 나타나는 표기용 정보입니다
- `support_teams` 컬렉션, 팀 코드, 초대 플로우 **모두 불필요**
- 작업량: **거의 없음** (입력 필드 2개 + 갤러리 표기)

##### 감수하는 것 (알고 계셔야 할 트레이드오프)

| 항목 | 영향 | 대응 |
|---|---|---|
| **중복 제출** | 한 팀에서 여러 명이 같은 산출물을 각각 올려도 시스템이 막지 못함 | 갤러리 공개 승인 단계(§4-3 ④)에서 담당자가 걸러냄 |
| **팀명 표기 흔들림** | 자유 입력이라 `제주AI수업연구회` / `제주 AI 수업연구회`로 갈릴 수 있음 | **팀명 자동완성** — 기존 입력값을 제안 목록으로 노출 (아래) |
| **팀 단위 집계 불가** | "팀별 산출물 몇 건" 같은 통계를 시스템이 내지 못함 | 시트에서 담당자가 수기 집계 |

> 💡 **작은 보완 제안**: 팀명 입력란에 **자동완성**을 붙이는 걸 권합니다. 같은 연도에 이미 입력된 팀명을 제안 목록으로 띄우면, 구성원들이 오타 없이 같은 팀명을 쓰게 됩니다. 갤러리에서 팀명으로 필터링할 때 결과가 정확해지고, 나중에 J2(팀 코드)로 승격할 일이 생겨도 데이터 정리가 쉬워집니다. **+0.5일**입니다.

##### 나중에 묶어야 할 필요가 생기면

`ownerName`과 `contributors`를 지금부터 **구조화된 필드로 저장**해 두면(자유 텍스트 한 덩어리가 아니라), 나중에 팀 코드 방식으로 올릴 때 기존 데이터를 그대로 활용할 수 있습니다. 아래 스키마가 그렇게 설계되어 있습니다.

#### ④ 데이터 모델 (모드 2 + J1)

```
support_applications/{appId}
  ├ uid                                       ← 항상 개인 1명
  ├ status, year, applicantInfo, projectPlan, files[]
  └ generatedPdfPath, sheetRowId, driveFolderId
                                              ↑ 팀 관련 필드 없음 (⏸ Q-21)

support_settlements/{id}                      ← **신청 1건 : 정산 1건**
  ├ applicationId, uid
  ├ status, totalAmount, bankInfo
  ├ driveFolderId                             ← 02_정산/{신청번호}/
  └ items [ { category, amount, receiptPath, driveFileId, memo } ]

support_outputs/{id}                          ← 산출물 (D-17)
  ├ submittedByUid, applicationId
  ├ activityType: 'individual' | 'team'
  ├ teamName?                                 ← 자유 입력 + 자동완성
  ├ contributors: [ { name, affiliation? } ]  ← 구조화 저장 (J2 승격 대비)
  ├ ownerName                                 ← 갤러리 표기용 (팀명 or 개인명)
  ├ category: 'output' | 'photo'
  ├ approved, approvedBy, approvedAt          ← 담당자 공개 승인 (§4-3 ④)
  └ tags[], visibility, files[], videoUrl, createdAt
```

> **`support_teams` 컬렉션은 만들지 않습니다.** J1의 핵심이 그것입니다.

##### ⏸ 확인 필요 — 신청서에도 개인/팀 구분이 필요합니까? (Q-21 연계)

J1에서는 **신청 단계에 팀 개념이 전혀 개입하지 않습니다.** 따라서 신청서에 `개인/팀` 선택을 둘 필요가 없을 수도 있습니다.

- 개인 신청과 팀 신청의 **지원금·심사 기준이 같다면** → 신청서에서 구분 불필요 (**더 단순**)
- **다르다면** → 신청서 Step 1에 구분이 필요하고, 안내·검증도 분기

→ **Q-21의 답이 이걸 결정합니다.**

**핵심**: `support_applications`와 `support_settlements`가 **개인 단위 1:1**로 유지되고, 팀은 산출물에만 **표기 정보**로 존재합니다.

#### ⑤ 파급 효과 (최소)

| **갤러리 (D-12)** | 팀명 우선 표기 + 팀명 필터 |

#### ⑥ 개인정보 — 대부분 해소

각자 본인이 가입해 본인 정보를 입력하므로, v0.9~0.10에서 지적했던 **대리 수집 문제가 사라집니다.**

> 다만 J1에서는 제출자가 **구성원의 이름을 텍스트로 기재**합니다. 이름만이라면 부담이 크지 않지만, 갤러리에 공개되는 정보이므로 제출 폼에 **"구성원 동의 하에 기재합니다"** 안내 한 줄을 두는 것을 권합니다.

## 5. 개발 마일스톤 (H-1 대기 상태 반영)

신청서 폼 명세(H-1)가 교수님 상의 후 확정되므로, **폼에 의존하지 않는 작업을 앞으로 당겨** 대기 시간을 죽이지 않도록 재배열했습니다.


### 🟠 6-2. 기술 리스크

**① Storage 직접 업로드의 보안 한계**
클라이언트→Storage 직접 업로드는 **파일 내용 검증·바이러스 검사·총 용량 제한이 불가**합니다. 신분증이 포함되므로 최소한 Storage Rules로 `size`·`contentType` 제한, 가능하면 Vercel Route Handler 또는 Cloud Functions 경유를 권장합니다.

**② 개인정보(신분증) 취급 — 법적 이슈**
- 신분증 사본은 **주민등록번호 뒷자리 마스킹 안내** 필수
- 수집·이용 동의, 보유기간, 파기 절차를 화면과 정책에 명시
- Storage 버킷 **공개 URL 금지** — 서명 URL 또는 인증 기반 접근만

**③ "관리자가 출력할 수 있는 형태"의 실체** (Q-3)
- (a) 브라우저 인쇄로 충분한가?
- (b) **PDF 파일로 저장·보관**해야 하는가? → 서버 사이드 PDF 생성(Puppeteer 등) 필요
- (c) 관공서 제출용 **직인·서명 이미지**가 필요한가?
→ (b)/(c)면 Phase 3 작업량이 크게 늘어납니다.

**④ 영상 호스팅**
Firebase Storage 직접 서빙은 **트래픽 비용이 급증**합니다. YouTube 미등록(비공개) 임베드 또는 Vimeo를 권장합니다.

**⑤ Firestore 복합 인덱스**
검색·필터 요구사항(예: "2026년 초등 신청건만")을 미리 알아야 인덱스를 설계할 수 있습니다. 사후 변경은 마이그레이션을 유발합니다.

**⑥ 첨부파일 감사 로그**
정산 서류는 감사 대상입니다. 업로드/다운로드 이력 로그 필요 여부 확인 요망.
