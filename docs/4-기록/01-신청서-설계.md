# 신청서 설계 (D-29) — 최소 구성

> 확정일: 2026-09-05 · 개정 2026-09-07 (D-43 회원 유형 · **D-44 초상권 동의 이동**)
> 이전 접근을 폐기하고 다시 잡은 문서입니다.

## 왜 다시 잡았나

프로그램마다 신청 항목이 다를 것을 전제로 "모든 경우를 담는 폼"을 설계하려다
**H-1이 확정되지 않는 한 아무것도 못 만드는 상태**에 갇혀 있었습니다.

그런데 재단이 어떤 프로그램을 기획하느냐에 따라 항목은 계속 달라집니다.
**변수를 미리 다 담으려는 시도 자체가 병목이었습니다.**

그래서 방향을 뒤집습니다 — **공고를 올려 접수를 시작할 수 있는 최소한**만 만듭니다.

---

## 1. 신청서에 들어가는 것

### ① 신청자 정보 — **입력하지 않습니다**

회원가입 때 이미 받았습니다. 신청 화면에서는 **확인만** 합니다.

| 항목 | 출처 |
|---|---|
| 이름 · 소속 · 학과·전공 · 신분(학번·학년 또는 직위) · 연락처 · 이메일 | 회원 정보 (**유형별로 다름 · D-43**) |
| 개인정보 수집·이용 동의 (O/X) | 회원 동의 이력 (가입 시) |

같은 걸 두 번 받지 않습니다. 정보가 틀렸으면 **회원정보 수정**으로 보냅니다.

> **⚠️ 제출 시점에 값을 복사해 신청서에 박아둡니다(스냅샷).**
> 나중에 회원이 연락처를 바꿔도 **제출 당시의 신청서는 그대로**여야 합니다.
> D-28의 PDF가 "원본"이 되려면 이게 전제입니다.

### ①′ 초상권 활용 동의 — **여기서 받습니다** (D-44)

가입 단계에서 함께 받다가 **신청 단계로 옮겼습니다** (09-07).

**왜 옮겼나** — 사진은 **특정 프로그램의 활동에서** 찍힙니다. 가입할 때 한 번
받아둔 포괄 동의는 *"어느 활동의 사진인가"* 에 답하지 못합니다. 사람마다
프로그램에 따라 판단이 다를 수도 있습니다 — 워크숍 사진은 괜찮아도 발표
영상은 곤란할 수 있습니다. 신청할 때마다 물으면 **그 프로그램의 사진에 대한
답이 그 신청서에 남습니다.**

| | |
|---|---|
| 답 | `applicant.portraitConsent` (신청서 문서) |
| 문구 버전 | `portraitConsentVersion` |
| 동의 시각 | `submittedAt` — **서버 시각**이라 별도 칸이 필요 없음 |

- **선택 항목이지만 답은 반드시 골라야** 제출됩니다. 안 고른 채 넘어가면
  기록상 **거부와 구분되지 않기** 때문입니다
- 동의하지 않아도 **신청·참여에 제한이 없습니다** (화면에 명시)
- 문구는 `components/apply/PortraitConsent.tsx` 한 곳에만 둡니다.
  **고칠 때는 `CONSENT_VERSION` 을 함께 올립니다** — 안 올리면 "어느 문구에
  동의한 것인지" 나중에 증명할 수 없습니다

> ⚠️ **회원 문서의 옛 초상권 기록은 이제 아무도 읽지 않습니다.**
> 스냅샷을 만들 때 회원 문서를 읽어버리면, 신청 화면에서 '동의하지 않음'을
> 골라도 시트에는 가입 때의 'O' 가 찍힙니다. **화면과 기록이 어긋나는데
> 아무도 눈치채지 못하는** 종류의 사고라 특히 조심할 곳입니다.

### ② 자유 기재란 — 프로그램이 요구할 때만

프로그램에 `noteLabel` 이 있으면 그 이름으로 **텍스트 입력란 하나**가 붙습니다.

```
noteLabel: "지원 동기"        → '지원 동기' 라는 이름의 입력란이 생김
noteLabel: "활동 계획 요약"    → 이름만 바꾸면 됨
noteLabel 없음                → 입력란 자체가 없음
```

**이 한 칸이 프로그램별 차이를 대부분 흡수합니다.** 항목이 달라질 때마다
코드를 고치는 대신 프로그램 문서의 글자만 바꿉니다.

### ③ 첨부 파일 — 프로그램이 요구할 때만

`attachmentGuide` 가 있으면 파일 첨부란이 붙습니다. 안내 문구도 거기 적습니다.
영수증·증빙서류가 여기로 들어갑니다.

## 2. 프로그램 문서에 추가되는 선택 필드

| 필드 | 유형 | 뜻 |
|---|---|---|
| `noteLabel` | string | 자유 기재란의 이름. 없으면 칸이 안 생김 |
| `noteRequired` | boolean | 자유 기재란 필수 여부 (기본 false) |
| `attachmentGuide` | string | 첨부 안내 문구. 없으면 첨부란이 안 생김 |
| `attachmentRequired` | boolean | 첨부 필수 여부 (기본 false) |
| 🆕 `cautionText` | string | **참가 유의사항**(D-98). 읽고 동의하는 글. 비면 구획이 안 생김. **D-99 이후 새 공고는 안 씀** — 아래 `formFields` 의 동의 칸이 대신하고 본문 스냅샷까지 남김 |
| 🆕 `formFields` | 배열 | **담당자가 화면에서 만든 칸들**(D-99). 배열 순서 = 화면 순서. 줄마다 `{fid, kind, label, body, multiline, options, required}` · `kind` 는 글 상자·첨부·동의·고르기(D-100 — `options` 는 고르기의 두 갈래) |

**전부 선택입니다.** 하나도 안 넣으면 "회원 정보 확인하고 제출" 만 남습니다.
그것만으로도 공고를 올리고 접수를 받을 수 있습니다.

## 3. 개인 / 단체에 대한 입장 변경

기존에는 `participationType` 으로 화면을 갈랐습니다. 그런데 **개인으로 접수받고
현장에서 팀을 짜는 방식**이 오히려 흔합니다. 팀 구성을 신청 시점에 알아야 한다는
전제가 틀렸던 것입니다.

**그래서:**

- `participationType` 필드는 **남겨두되 기본값 `individual`**
- 신청서는 **개인 기준 한 가지**만 만듭니다
- 팀원 명단 입력은 **만들지 않습니다.** 실제로 필요한 프로그램이 나타나면 그때 붙입니다
- 상세 화면의 단체 안내 문구는 `group` 일 때만 계속 표시 (정보 제공용)

*(D-16/D-17에서 정한 "팀이어도 각자 신청" 원칙과 어긋나지 않습니다. 오히려
 그 원칙을 끝까지 밀면 신청 시점에 팀 정보가 필요 없다는 결론이 나옵니다.)*

## 4. 흐름

```
프로그램 상세 → [신청하기]
   ↓
신청서 화면
   · 내 정보 확인 (수정 불가, 틀리면 회원정보 수정으로)
   · 동의 여부 표시
   · [자유 기재란]      ← 프로그램이 요구할 때만
   · [파일 첨부]        ← 프로그램이 요구할 때만
   ↓ 제출
support_applications 문서 생성 (status: submitted, 정보 스냅샷 포함)
   ↓
마이페이지 → 내 신청 현황에서 상태 확인
```

**임시저장은 넣지 않습니다.** 입력할 것이 거의 없어서 의미가 없고,
"작성 중" 상태가 늘면 담당자가 봐야 할 상태만 늘어납니다.

**한 프로그램에 중복 신청은 막습니다.** 이미 신청한 프로그램은 상세 화면에
"신청 완료"로 표시되고 마이페이지로 안내합니다.

## 4-1. 제출 시 PDF 원본 (D-28) — 구현 완료

제출 버튼을 누르면 **화면 밖에 A4 크기로 그려둔 신청서**를 이미지로 캡처해
PDF로 만들고, 첨부 파일과 함께 Storage에 올린 뒤 문서를 씁니다.

```
support/applications/{uid}/{신청번호}/
  ├─ 신청서.pdf          ← 제출 시점 원본
  └─ {시각}_{파일명}      ← 첨부 서류
```

- **한글이 깨지지 않습니다.** jsPDF에 한글을 직접 그리려면 폰트를 번들에 심어야
  하는데, 화면을 캡처하면 브라우저 폰트를 그대로 씁니다
- **PDF 생성이 실패해도 제출은 진행됩니다.** PDF는 사본 성격이고, 이것 때문에
  학생이 신청을 못 하게 되는 쪽이 더 큰 문제입니다
- 문서 ID를 **미리 만들고 파일부터 올린 뒤** 마지막에 문서를 씁니다.
  제출된 신청서에서 본인이 바꿀 수 있는 칸은 규칙이 못 박아 두어서(4-2), 문서를
  먼저 만들고 첨부 목록을 덧붙이는 순서로는 막힙니다

## 4-2. 마감 전 본인 수정 (D-73 · 09-16) — 구현 완료

교수님(09-14): "마감 전까지는 신청 내역을 수정할 수 있게." iSERI(09-15): 범위는
**신청서 내용만**(팀 활동 중 변동 — 팀명·역할·계획), 시점은 **접수 마감 전까지만**.

| 칸 | 수정 | 왜 |
|---|---|---|
| 프로그램 전용 항목 · 자유 기재란 | **가능** | 신청서 내용 |
| 첨부 · 신청자 정보 사본 · 초상권 동의 | 불가 | 제출 시점 원본(D-28) · 동의는 버전·시각과 묶임. 바꾸려면 취소 후 재신청 |

**조건**은 본인 취소와 같다(`canEditMyself` ≡ `canCancelMyself`): 미처리/보완 요청 ·
공개 프로그램 · 접수 기간 안. 하나 더 — 전용 양식 프로그램인데 **원래 값(`formValues`)이
없으면** 폼을 되살릴 수 없어 열지 않는다(09-16 이전 제출분. 실제 제출 건 없음).

**저장 방식** — 같은 문서를 제자리에서(`updateMyApplication`). 문서 ID·열쇠·시트 줄이
그대로라 중복이 없다. 규칙은 바꿀 수 있는 칸을 `note · noteLabel · formData · formValues ·
generatedPdfPath · pdfHistory · editCount · lastEditedAt · updatedAt` 아홉 개로 못 박는다
(취소 조항과 같은 `affectedKeys().hasOnly` 방식). 예전의 "draft·revision 이면 본인 update
허용" 조항은 칸 제한이 없어 이 조항으로 **대체**했다.

```
support/applications/{uid}/{신청번호}/
  ├─ 신청서.pdf        ← 최초본 (v1)
  ├─ 신청서-v2.pdf     ← 1회 수정본   generatedPdfPath 는 최신본, 옛 경로는 pdfHistory
  └─ 신청서-v3.pdf     ← 2회 수정본
```

**시트·드라이브** — `sheetRowId` 가 있으면 그 줄을 **덮어쓰고**(정산 탭 방식), 드라이브
PDF 는 appProperties 의 신청번호로 찾아 **같은 파일의 내용을 교체**(링크·이름 불변).
시트 Q열 「수정」에 `2회 · 시각`. 동기화 API 의 "이미 올렸으면 건너뜀"은 뺐다 — 줄
덮어쓰기라 재호출이 안전하다.

**화면** — 마이페이지 카드에 [신청 내용 수정](조건 만족 시, 취소 링크 옆) →
`/apply/{프로그램}?edit=1` 로 **신청 화면을 수정 모드로** 연다. 신청자 정보·첨부·초상권은
읽기 전용, 전용 항목·기재란만 입력, [수정 내용 저장] → PDF 새 버전 → 저장 → 시트 갱신
→ 마이페이지 "수정했습니다". 담당자 목록에 「수정됨 · 시각 · n회」 배지. PDF 에는
"수정본 (n회)" 줄이 붙고 신청일은 최초 제출일.

## 6. 이 설계의 전제

**신청서가 프로그램마다 크게 달라지면 이 구조로는 부족합니다.**
그때는 "항목을 담당자가 직접 정의하는 폼 빌더"가 필요한데, 그건 별도 사업 규모입니다.
지금은 **자유 기재란 하나 + 첨부 하나**로 버티고, 못 버티는 프로그램이
실제로 나타나면 그때 다시 논의합니다.

### 🔄 2026-09-22 개정 (D-99) — 그 프로그램이 나타났습니다

해커톤(AI-EDU Next Class)이 트랙·과제·글자 수 제한을 요구해 **전용 양식을 코드로** 만들어야
했고(D-96), 「참가 유의사항」은 코드 상수로 뒀다가 문구 한 줄 바꾸는 데 배포가 필요해져
공고 칸으로 뺐습니다(D-98). 위 문단의 조건이 충족된 것으로 보고 **부분적으로** 뒤집었습니다.

> 🔴 **경계 — 이 줄이 기준선입니다**
> 담당자가 화면에서 정의할 수 있는 것은 「이름 + 안내문 + 필수 여부」가 붙은
> **글 상자 · 첨부 · 동의 세 가지뿐**입니다. 선택지·분기·계산·형식 검사가 필요해지면
> 그것은 여전히 `lib/forms` 의 **전용 양식(코드)** 으로 만듭니다. D-50 등록소는 없애지 않습니다.

**폼 빌더 전체를 만들지 않은 이유는 그대로입니다** — 선택지를 열면 「보기 추가·삭제·순서」 UI 가
칸 안에 또 생기고, 「기타(직접 입력)」·「여러 개 고르기」·「이걸 고르면 저게 나오기」가
반드시 따라옵니다. 그것이 D-29 가 막혔던 지점입니다.

### 🔧 새 전용 양식을 더할 때 채워야 하는 것 (09-25)

`lib/forms/index.ts` 의 `PROGRAM_FORMS` 에 줄을 더합니다. **단체 프로그램용이면
`groupNotice` 를 반드시 넣으세요** — 세 항목 전부입니다.

| 항목 | 어디에 나오나 |
|---|---|
| `short` | **목록 카드·홈 카드**의 「신청」 한 마디 (예: 「팀원이 각자」) |
| `howToApply` | **상세 요약**의 「신청 방식」 한 줄. `· 최대 N명` 은 화면이 붙입니다 |
| `body` | **「단체 프로그램 신청 안내」** 빨간 상자 본문 |

**셋 다 `GroupNotice` 타입이라 하나만 빠뜨려도 빌드가 실패합니다.** 09-25 에 `short` 를
`GROUP_NOTICE` 에만 더하고 전용 양식 쪽 타입은 그대로 뒀더니, **해커톤 카드가 계속
「팀 단위」로 나오는데 컴파일러가 아무 말도 하지 않았습니다.** 타입을 합쳐서 막았습니다.

⚠️ **`groupNotice` 자체는 선택 항목입니다** — 개인 프로그램용 양식은 필요 없으니까요.
그래서 **단체용인데 빠뜨리는 것은 타입으로 못 막습니다.** 그 경우 담당자가 고른
「신청은 누가 하나」로 조용히 되돌아가서, 기본값(`leader`)이면 **양식은 각자 신청인데
화면은 「팀 단위」** 가 됩니다. 개발 중에 **콘솔 경고**가 뜨게 해 두었습니다
(`groupNoticeOf`) — 새 양식을 만들면 로컬에서 바로 보입니다.

🔴 **화면에서 짐작하지 마세요.** 목록 카드·홈 카드·상세는 **모두
`groupNoticeOf(program)` 한 함수**를 씁니다. 예전에는 상세만 순서를 알고 카드는
「팀 단위」를 박아 둬서 **같은 공고가 두 말을 했습니다.** 새 화면에서 단체 여부를
표시할 일이 생기면 그 함수를 부르세요.

### 🔄 2026-09-25 개정 (D-100) — 「고르기」를 넣고 선을 옮겼습니다

위 경계가 **사흘 만에 두 번 더 깨졌습니다.** 데이터 디깅 캠프 하나에서:

| 필요했던 것 | 동의 칸으로 우회했더니 |
|---|---|
| 팀 대표자 / 팀원 | 「저는 대표자입니다」 체크박스 — **미체크가 「팀원」인지 「안 봤음」인지 모른다** |
| 오픈소스 공개 동의함 / 동의하지 않음 | 선택 동의 — **거부한 사람과 지나친 사람이 같은 기록으로 남는다** |

둘째 것은 코드에 이미 모순으로 드러나 있었습니다. `sealBodies`(옛 `sealConsents`)의 주석은
*"거부도 반드시 기록한다 — 기록이 없는 것과 거부한 것은 다르다"* 라고 해 놓고,
바로 아래에서 `if (out[f.fid] === undefined) out[f.fid] = 'n'` 으로 **무응답을 거부로**
적고 있었습니다. 필수 동의에서는 드러나지 않던 결함이 **선택 동의에서 터졌습니다.**
초상권(D-44)이 버튼 두 개인 이유가 정확히 이것인데, 자율 칸에서 같은 함정을 다시 밟았습니다.

> 🔴 **새 경계 — D-99 의 줄을 이렇게 고칩니다**
> 담당자가 화면에서 정의할 수 있는 것은 「이름 + 안내문 + 필수 여부」가 붙은
> **글 상자 · 첨부 · 동의 · 고르기(두 갈래) 네 가지**입니다.
> **셋 이상 고르기 · 분기 · 계산 · 형식 검사**는 여전히 전용 양식(코드)입니다.

**왜 두 갈래로 못 박았나** — 개수를 열면 담당자 화면 안에 「보기 추가·삭제」 UI 가 또
생깁니다(위 문단이 막은 그것). 필요했던 두 사례가 **모두 두 갈래**였습니다. 셋이
필요한 사례가 나오면 그때 늘립니다 — 「사례가 두 번 나오면 다시 논의」와 같은 규칙입니다.

**답으로는 고른 「글자」를 저장합니다**(index 가 아닙니다). 담당자가 선택지 이름을 고치면
옛 답이 어느 쪽도 아니게 되어 **다시 고르게** 됩니다. index 를 쓰면 이름을 고친 순간
옛 답의 뜻이 **조용히 바뀝니다** — 국비 사업 기록에서 가장 위험한 종류의 변화입니다.

**고르기도 동의처럼 「읽은 글」을 얼립니다**(`sealText`). 본문뿐 아니라 **선택지 두 개까지**
포함해서 얼리므로, 담당자가 「동의함」을 「승인」으로 바꾸기만 해도 다시 묻습니다.
⚠️ **동의의 얼린 값은 건드리지 않았습니다** — 기존 신청서에는 `body` 만 보관돼 있어서,
여기에 뭘 더 이어 붙이면 **이미 낸 동의 전부가 「본문이 바뀐 것」으로 판정**됩니다.

**고르기에는 답을 대신 채우지 않습니다.** 안 고르면 답이 없는 채로 두고 신청서에 줄도
만들지 않습니다. 거부를 반드시 남겨야 하는 항목이면 **필수로 두고 「동의하지 않음」을
고르게** 합니다 — 그래서 「+ 고르기」로 만든 칸은 **필수가 기본값**이고, 필수를 끄면
담당자 화면에 경고가 붙습니다.

**시트·규칙·PDF 는 그대로입니다** — 답이 `formData`·`formValues` 로 가고 둘 다 이미
`firestore.rules` 허용 목록에 있습니다. 열도 늘지 않습니다(D-50 의 목적). PDF 의
「동의한 내용」 상자만 **「동의·선택한 내용」** 으로 이름이 바뀌고 고르기도 함께 들어갑니다.

**첨부만 공고당 하나**입니다. 글자 답은 `formData` 한 줄로 끝나지만, 파일은 Storage 경로·
드라이브 폴더·PDF 목록·개수 제한이 얽혀 있어 칸을 늘리면 다섯 곳이 동시에 흔들립니다.

**옛 칸(`noteLabel`·`attachmentGuide`·`cautionText`)은 이주하지 않고 공존**합니다.
`note` 는 시트 N열과 PDF 전용 상자를 갖고 있어 옮기면 옛 답과 새 답이 다른 열로 갈립니다.
담당자 화면에서 **값이 있을 때만** 「옛 방식 칸」으로 보이고, 새 공고는 만들 길이 없습니다.
