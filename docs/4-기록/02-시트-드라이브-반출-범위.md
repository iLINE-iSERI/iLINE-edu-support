열 순서가 바뀌면(09-16 N~Q) 코드가 머리글을 다시 쓰지만 **옛 줄의 값은 옛 순서 그대로**다 —
그 줄이 다음에 동기화될 때 새 순서로 고쳐진다. 시험 줄이면 정리 스크립트로 지운다.

**왜 항목마다 열을 만들지 않고 한 칸에 몰아넣나 (D-50)**

「AI-EDU 연구반」은 팀명·역할·수업 유형·학교급·교과 등 **전용 항목이 8개**
입니다. 이걸 열 8개로 늘리면 **다른 프로그램 줄에서 전부 빈칸**이 됩니다.
프로그램이 셋만 되어도 시트는 빈칸투성이가 되고, 담당자는 가로로 한참
스크롤하게 됩니다.

**D-43에서 똑같은 일을 겪었습니다** — 학번·전공·학년 열이 교원 회원에게
빈칸이 됐습니다. 그때 배운 것을 여기 적용합니다: **프로그램마다 달라지는
것은 열로 만들지 않습니다.**

한 칸 안은 이렇게 보입니다.

```
팀명: 제주AI융합
팀에서의 역할: 팀장
융합 수업 유형: 데이터 과학 (지역 공공데이터 분석, 문제 해결 등)
대상 학교급: 중학교
...
```

> 📌 항목이 늘어도 **시트 구조는 그대로**입니다. 프로그램마다 다른 것을
> 시트로 집계해야 할 일이 생기면, 그때는 시트가 아니라 **담당자 화면에
> 내려받기를 붙이는 편**이 낫습니다 — 시트 열을 늘리는 것은 되돌리기 어렵습니다.

**학번·전공·학년 세 열을 왜 없앴나 (D-43)**
학생만 받던 때는 그 세 열이 늘 채워졌습니다. 그런데 **교원·일반 회원이
생기면서** 신청자의 절반쯤은 학번도 학년도 없게 됩니다. 열을 그대로 두면
시트에 빈칸이 줄줄이 남고, 담당자는 그 빈칸이 **"안 적은 것"인지 "물어보지
않은 것"인지** 구분할 수 없습니다. 그래서 **유형(D)을 먼저 보여주고**,
유형에 맞는 값이 들어가는 **소속 / 학과·전공 / 신분** 세 열로 바꿨습니다.

> ⚠️ **이미 줄이 쌓인 시트가 있다면 머리글이 자동으로 바뀌지 않습니다.**
> 머리글은 첫 줄이 비어 있을 때만 넣습니다. 옛 시트는 A1:P1 을 직접
> 고치거나, 시험 데이터를 정리할 때(🟣F) 첫 줄째 지우면 다음 제출에서
> 새 머리글이 들어갑니다.

**동의 여부를 O/X로 내보내는 이유**
초상권 동의는 **활동사진을 자료집·홈페이지에 쓸 수 있는지 판단하는 근거**입니다.
담당자가 사진을 고를 때 시트에서 바로 확인할 수 있어야 실수가 없습니다.
거부(X)도 반드시 표시합니다 — 기록이 없는 것과 거부한 것은 다릅니다.

> ⚠️ **초상권 동의는 신청 건마다 다릅니다 (D-44, 09-07).**
> 가입할 때 한 번 받던 것을 **프로그램 신청 단계로 옮겼습니다.** 사진은
> 특정 프로그램의 활동에서 찍히고, 같은 사람이 A 프로그램은 동의하고
> B 프로그램은 거부할 수 있습니다.
>
> 그래서 **"이 사람이 동의했는가"로 판단하면 안 됩니다.** 사진을 올릴 때는
> **그 사진이 나온 프로그램의 줄**을 보세요. 한 사람의 이름이 시트에 여러 줄
> 있을 때, 줄마다 L 열의 값이 다를 수 있습니다.

**신청 탭과 다른 점 — 학번·학년·직위를 나눴다.** 신청 탭은 D-43 에서 「신분」 한 칸으로 합쳤다(빈칸이 「안 적은
것」인지 「안 물은 것」인지 모르게 되어서). 회원 탭은 **통계용**이라 「3학년만」 거르기·학년별 세기가 되어야 하고,
바로 앞 「회원 유형」 칸이 빈칸의 까닭을 말해 주므로 나눈다.

**넣지 않는 것** — 이메일(10-03 운영진: 필요 없음) · 개인정보 수집·이용 동의 O/X(가입 때 필수라 모두 O — 통계에
쓸모없음. 동의 기록은 사이트에 그대로) · 가입 방식 · 동의 문구 판·시각 · 신청 이력(신청 탭에 있음) · **테스트 계정 줄**(D-111).

**언제 쓰나 — 자동 + 어긋남 표시 + [전체 반영]** (10-03 sunbell — 「누를 때만」·「하루 한 번」과 비교한 뒤 정함)
- **자동** — 가입 완료(2단계까지) · 회원정보 수정 · 탈퇴 때 그 회원의 줄을 쓴다(회원 화면이 저장 뒤 서버에 요청).
  담당자 지정·회수(D-120)는 **서버가 직접** 그 줄의 「구분」을 고친다
- **[전체 반영]**(회원 관리 화면) — ① 켤 때 이미 가입해 있던 회원을 **처음 한 번** 올림 ② 자동으로 쓰다 어긋났을 때 고침.
  누르는 순간의 사이트 회원 전부를 기준으로 맞추고, 몇 번 눌러도 결과가 같다(회원번호로 자기 줄을 찾음). 같은 회원번호가
  두 줄이면 뒤 줄을 지운다(누르는 순간 가입이 겹친 드문 경우). **사이트에서 지워진 회원**(시험 계정 정리 등)의 줄도 지운다 —
  사본만 남아 있으면 안 되므로. A열 값이 회원번호 모양이 아니면(사람이 적은 메모 등) 건드리지 않는다
- ⚠️ **탈퇴를 처리하는 화면이 아직 없다**(남은 일 ③) — 지금은 Firebase 콘솔에서 손으로 하는데, 그때는 「고친 시각」이 바뀌지
  않아 자동 반영도, 「시트와 다름」 표시도 일어나지 않는다 → 콘솔로 탈퇴 처리했으면 **[전체 반영]**. 탈퇴 화면을 만들 때
  자동 반영을 함께 건다
- **어긋남 표시** — 사이트가 회원마다 「시트에 마지막으로 반영한 시각」과 실패 사유를 적어 둔다. 실패했거나, 회원 정보가
  그 시각보다 나중에 바뀌었거나(저장 뒤 브라우저를 닫아 아예 못 쓴 경우), 반영 기록이 없으면 「시트와 다름」 —
  **관리 줄 「회원」 옆 숫자** · 회원 관리 맨 위 상자 · 그 회원 줄 배지. 방금 저장해 쓰는 중인 회원은 2분 기다려 준다

**줄 다루기**
- 줄은 **A열의 회원번호로** 찾는다(D-109). 담당자가 정렬하거나 줄을 옮겨도 자기 줄을 찾는다
- **새 줄은 A열에서 마지막으로 값이 있는 줄 바로 아래에** — 구글이 「표의 끝」을 찾게(append) 두면 중간 빈 줄에 끼워 쓸 수
  있어서(10-03 sunbell 지적). 처음엔 직접 쓰고 다시 읽어 확인했는데, **D-127(10-07)부터 다섯 탭 모두 「빈 줄을 끼워 넣고
  채우기」를 한 번의 요청으로** 한다 — 동시에 와도, 필터가 켜져 있어도 덮어쓰지 않는다(다른 탭의 append 가 10-05 필터 때문에
  해커톤 7건을 덮어쓴 일이 계기)
- **일반 회원이 테스트 계정이 되면 그 줄을 지운다**(행 삭제 — 아래 줄이 올라온다 · 10-03 sunbell). 원래 시트에 있으면 안 되는
  줄이라 잃는 기록이 없다(취소된 신청처럼 남겨야 하는 기록과 다름). 지우는 일은 **[전체 반영]의 맨 끝에 한꺼번에** —
  「줄 찾기 → 쓰기」 사이에 위 줄이 지워져 다른 줄을 덮어쓰는 드문 겹침을 줄이려고

**켜는 스위치** — Vercel 환경변수 `NEXT_PUBLIC_MEMBER_SHEET_ENABLED=1`(sunbell 이 켬 · 기본 꺼짐 · 바꾸면 다시 배포).
꺼져 있으면 자동·[전체 반영] 모두 시트에 쓰지 않고 어긋남 표시도 하지 않는다. 회원 관리 화면에 「회원 시트 연동: 꺼짐」 한 줄.
화면 버튼으로 두지 않은 까닭 — 담당자가 개정 시행 전에 실수로 켤 수 있어서.

**회원 탭을 다른 스프레드시트에 두기(선택)** — 환경변수 `MEMBER_SHEET_ID` 에 다른 스프레드시트 ID 를 넣으면 「회원」 탭이
그쪽에 생긴다(없으면 운영 시트). 로컬 시험 때 운영 시트에 회원 탭을 만들지 않으려고 둔 것 — `.env.local` 에만.

**드라이브에는 올리는 파일이 없다.**

## 2. 공유 드라이브에 올리는 파일

```
[공유 드라이브] 교원양성지원사업
├─ 신청/       ← 구현 완료 (09-05) · 설계 때 이름 01_신청
│   └─ 프로그램명_이름_2609051642.pdf
└─ 정산/       ← 구현 완료 (09-12 · D-65 · D-117) · 설계 때 이름 02_정산
    └─ 프로그램명/
        └─ 팀명/  (개인 프로그램이면 이름/ · 겹치면 '이름 (2)')
            ├─ 01차_홍길동_영수증_01_원래이름.jpg
            ├─ 01차_홍길동_회의록_01_원래이름.pdf
            ├─ 01차_김철수_영수증_01_원래이름.jpg   ← 같은 팀원 — 회차는 사람마다
            └─ 02차_홍길동_영수증_01_원래이름.jpg
```

**정산 폴더는 팀(개인 프로그램이면 사람)마다 폴더입니다** (D-117 · 09-30). 한 사람이
여러 번 내고, 팀원들이 따로 내므로 한 폴더에 여러 사람·여러 회차가 모입니다. 그래서
파일 이름 앞에 **회차 · 이름 · 증빙서류 종류**를 붙입니다(회차는 두 자리).

- 팀·사람 폴더는 이름이 아니라 숨은 속성(팀명 또는 회원 번호의 해시 `uk`)으로 찾으므로
  같은 이름의 사람·팀이 있어도 섞이지 않습니다.
- 파일은 숨은 속성(Storage 경로의 해시 `rk`)으로 알아보아 **재제출·재시도 때 같은 파일이
  두 번 올라가지 않습니다.** 파일마다 **정산번호(`sid`)** 도 붙어, 재제출 때 뺀 파일을
  휴지통으로 보낼 때 **그 정산의 파일끼리만** 비교합니다(다른 회차·다른 팀원 파일은 건드리지 않음).
- 사람이 폴더에 직접 넣은 파일은 건드리지 않습니다.
- D-117 전에는 정산 1건 = 사람 폴더 1개(`프로그램명/이름/01_파일명`)였습니다.

폴더 ID 는 환경변수 `DRIVE_SETTLEMENT_FOLDER_ID`(정산) · `DRIVE_FOLDER_ID`(신청).

> 📌 **폴더 이름은 「신청」·「정산」입니다** (09-29 iSERI 가 바꿈 — 그 전 「01_신청」·「증빙서류」).
> 코드는 **ID로만** 찾으므로 이름은 무엇이든 됩니다. 이름을 바꿔도 ID는 그대로라 계속 동작합니다.
> 🔴 폴더를 **새로 만들어 옮기면** ID가 바뀌어 환경변수도 바꿔야 합니다 — 이름만 바꾸세요.

**올리는 것**: 신청서 PDF(D-30) · 영수증·회의록 등 **정산 증빙서류**

**올리지 않는 것**: 아래 §3 참고

> **Q-3′ 해소 (D-30)** — 신청서 PDF를 드라이브에 올리고 시트에 링크를 넣습니다.
> 담당자가 시트에서 바로 열 수 있습니다.
>
> **파일명에 신청번호는 넣지 않습니다.** 사람이 읽기 쉽도록
> `프로그램명_이름_날짜시각.pdf` 로 짓고, 신청번호는 드라이브 파일의
> 숨은 속성(`appProperties`)에 넣어 재시도 시 같은 건을 알아보는 데만 씁니다.
> 역추적이 필요하면 시트의 `신청번호` 열을 보면 됩니다.
>
> **원본은 언제나 Firebase Storage** 이고 드라이브 쪽은 사본입니다.

## 4. ✅ 해소된 확인 사항 (D-38 · 2026-09-06)

### 4-1 / 4-2 결론 — 민감 서류는 사이트가 받지 않습니다

| 무엇 | 어떻게 | 왜 |
|---|---|---|
| **은행명 · 계좌번호 · 예금주** | **사이트에서 글자로**, **정산 단계에** 입력 | 지급에 필요한 최소 정보 |
| **통장 사본** | ⛔ **아예 받지 않음** (09-06 회계 확인) | 이체 시 예금주가 자동 확인됨 |
| **신분증 사본** | ⛔ **아예 받지 않음** (09-06 교수님 확인) | 소속·학과·신분 정보로 자격이 확인됨 |
| **영수증 등 지출 증빙** | 사이트 업로드 → 드라이브 `02_정산`(지금 이름 「정산」) | 개인 신원 정보가 아님 |

**계좌를 정산 단계에서 받는 이유**: 계좌는 **선정된 사람만** 필요합니다.
신청 시점에 받으면 미선정자 것까지 보유하게 됩니다. 신청 100명 중 20명
선정이면 **쓸 일 없는 계좌 80건**을 들고 있는 셈입니다.

**계좌번호는 법적으로 '민감정보'가 아닙니다.** 민감정보(사상·건강·생체 등)도
고유식별정보(주민등록번호 등)도 아닌 일반 개인정보이고, 신용정보법상
개인신용정보로 다뤄집니다. 그래서 특별한 별도 절차는 아니지만 **보통의
개인정보보다는 조심해서** 다룹니다 — 아래 §3 반출 금지에 그대로 남습니다.

### 4-2′. 정산 화면 구성 (09-06 확정 · D-39)

```
지급 계좌   은행 · 계좌번호 · 예금주      ← 필수 · 사이트 안에서만
영수증      파일 업로드 (여러 장)         ← 선택 · 드라이브 02_정산
```

**영수증은 선택입니다 (D-41).** 지출 증빙이 필요한 회차도, 계좌만 받으면
되는 회차도 있습니다. 프로그램마다 설정을 두는 대신 **항상 낼 수 있게** 두어
화면을 하나로 유지했습니다. 무엇을 내야 하는지는 **공고문이 안내**하고,
어긋나면 담당자가 사유를 적어 반려합니다.

**지출 내역을 줄 단위로 받지 않습니다.** 신청서에서와 같은 판단입니다(D-29) —
회차마다 달라지는 항목을 미리 예측해 폼에 넣으면 만들다 막힙니다.
필요해지면 그때 칸을 늘립니다.

> **금액 칸을 두지 않기로 확정했습니다 (09-06).** 총액 한 칸을 제안했으나
> 최소 구성을 유지하기로 했습니다. 대신 **담당자가 영수증을 열어 금액을 읽고
> 직접 합산**하게 됩니다. 건수가 늘어 그 작업이 부담이 되면 **숫자 한 칸을
> 추가**하는 것으로 해결됩니다 — 입력칸 하나, 시트 열 하나입니다.

### 4-3. ✅ 결론 — 사이트가 다루는 개인정보가 확정되었습니다

**민감 서류를 하나도 받지 않습니다.** 통장 사본·신분증이 모두 빠지면서,
사이트 밖(이메일) 접수 절차도 **만들 필요가 없어졌습니다.**

사이트가 보유하는 것은 다음이 전부입니다.

| 언제 | 무엇 |
|---|---|
| 가입 | 이름 · 소속 · 학과·전공 · 신분(학번·학년 또는 직위) · 연락처 · 이메일 · **개인정보 동의** |
| 신청 | 위 정보의 사본 + **초상권 동의**(D-44) + (프로그램이 요구하면) 자유 기재·첨부·**전용 항목**(D-50) |
| **정산** | **은행명 · 계좌번호 · 예금주 + 영수증** — 선정자만 |

계좌는 **시트·드라이브로 내보내지 않으므로** 담당자가 사이트 안에서 봅니다
(`/staff/settlements`, 누를 때만 표시 — 구현 완료 09-06).
지급이 끝나면 보유기간에 따라 파기합니다.

## 5. 운영 시 지켜야 할 것

- 스프레드시트 **공유 설정은 "제한됨"** — 링크 있는 사람 공유 금지, 지정 계정만
- 공유 드라이브 **외부 공유** — 서비스 계정이 조직 외부로 분류되어 전면 차단은
  불가. 대신 **'멤버가 아닌 사용자 액세스'를 차단**해 실질적으로 막았습니다.
  자세한 배경과 협의 방안은 `docs/4-기록/03-드라이브-공유-정책.md`
- 공유 드라이브 **멤버 목록을 주기적으로 점검** — 위 설정의 대체 통제 수단
- 멤버 추가·제거 절차 문서화 — **인수인계·퇴사 시 즉시 제거**
- 보유기간 만료 시 **Storage와 드라이브 두 곳 모두** 파기
