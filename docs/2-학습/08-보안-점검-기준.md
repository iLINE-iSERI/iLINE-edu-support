## 0. 한 줄 요약

**서버가 어떤 칸을 보고 판단한다면, 회원은 그 칸을 쓸 수 없어야 한다.**
그리고 **화면이 막는 것은 규칙도 막아야 한다.** 둘 중 하나라도 빠지면, 개발자 도구를 여는

### 사례 1 — 「시험」 표시를 회원이 스스로 붙일 수 있었다 (D-111)

| | |
|---|---|
| **의도** | 테스트 계정이 낸 신청·정산·산출물·문의는 시트·드라이브로 보내지 않는다 |
| **구현** | 네 동기화 경로(`app/api/sync/*/route.ts`)가 `snap.get('sheetSkipped') === 'tester' \|\| isTesterUid(주인)` 이면 건너뛴다 |
| **빈틈** | 앞쪽 조건은 **문서에 적힌 값을 그대로 믿는다.** 그런데 신청서·정산·산출물의 **create 규칙은 넣을 수 있는 칸을 제한하지 않는다** → 일반 회원이 `sheetSkipped: 'tester'` 를 넣어 제출할 수 있다 |
| **결과** | 그 건은 시트·드라이브에 안 올라가고, 담당자 목록엔 「시험」으로 보여 **놓치기 쉽다** |
| **어긋난 곳** | `lib/server/admin.ts` 의 `isTesterUid` 주석은 *"신청서에 적힌 값을 믿지 않고 회원 문서를 직접 읽는다"* 고 말한다. **주석의 의도와 라우트의 조건이 달랐다** |
| **1:1 문의는 안전** | 문의 create 규칙은 `keys().hasOnly([...])` 로 칸을 못 박아 두었다 — 이것이 올바른 꼴 |

**교훈** — 서버 전용 칸(`sheetSkipped`)을 도입하면서 **「그 칸을 누가 쓸 수 있는가」를 규칙에서 확인하지 않았다.**
서버 코드와 규칙이 서로 상대가 막아 줄 거라고 믿은 경우다.

### 사례 2 — 「영수증 한 장 이상 필수」가 화면에만 있었다 (D-108)

| | |
|---|---|
| **의도** | 계좌를 없앤 뒤 증빙이 정산의 전부이므로 한 장 이상 필수 |
| **구현** | 정산 화면(`components/settlement/SettlementSection.tsx`)에서만 검사 |
| **빈틈** | 정산 create·본인 재제출 규칙에 `receipts` 개수 확인이 없다 → 화면을 거치지 않으면 파일 없는 정산이 들어간다 |

**교훈** — 규칙 파일 주석에 이미 *"화면 차단은 최종 방어선이 아니다"* 라고 적혀 있다(신청서 create).
**요구 조건을 바꿀 때(선택 → 필수) 규칙도 같이 바꿨는지** 확인하지 않았다.

## 2. 원칙 다섯

1. **서버가 믿는 칸은 서버만 쓴다.** Admin SDK 경로(`app/api/**`)가 문서의 어떤 칸을 보고 동작을
   바꾼다면, 그 칸은 규칙에서 회원이 **만들 때도 고칠 때도** 못 쓰게 한다.
   - 만들 때: `!('칸' in request.resource.data)` 또는 `keys().hasOnly([...])`
   - 고칠 때: `affectedKeys().hasOnly([...])` 에서 빼거나, `request.resource.data.get('칸', '') == resource.data.get('칸', '')`
   - ⚠️ 고칠 때 `!('칸' in request.resource.data)` 를 쓰면 **서버가 이미 그 칸을 넣은 문서는 본인이 다시 못 고친다**
     (update 의 `request.resource.data` 는 기존 칸까지 포함한 결과 문서다). 「바꾸지 못함」으로 쓴다.
2. **create 규칙도 칸을 제한한다.** 지금 update 는 대부분 `affectedKeys().hasOnly` 로 잘 막혀 있지만,
   create 는 `uid`·`status` 만 확인하는 곳이 많다. **create 가 더 넓은 문**이다.
3. **화면 검사를 추가·강화하면 규칙에도 넣는다.** 필수 여부, 개수, 길이, 허용 값.
   화면은 친절을 위해, 규칙은 방어를 위해 — 두 곳에 같이 있어야 한다.
4. **Admin SDK 는 규칙을 건너뛴다.** 서버 경로는 요청자가 주인인지·담당자인지를 **직접** 확인하고
   (`verifyRequester`), 판단에 쓰는 사실은 **출처 문서**(회원 문서 등)에서 읽는다. 회원이 쓴 사본을 믿지 않는다.
   - 좋은 예: 문의 동기화는 이름·이메일을 **회원 문서에서** 읽는다(`app/api/sync/inquiry`)
   - 좋은 예: D-109 이후 `sheetRowId` 는 **힌트로만** 쓰고 A열에서 다시 확인한다
5. **주석이 말하는 보장과 코드가 하는 일이 같은지 본다.** 사례 1은 주석이 맞고 코드가 달랐다.
   리팩토링 때 「이 주석이 약속하는 것을 이 줄이 실제로 지키나」를 확인한다.

- **알고 두는 한계 (고치지 않음)** — 자율 칸의 필수 답·필수 동의 검사(`fields.ts` `firstProblem`)는 **화면에만** 있다(원칙 3). 공고마다 칸이 달라 규칙으로 옮기기 어렵고(규칙엔 반복문이 없다), 빠진 답은 신청서에 그대로 드러나 담당자에게 보인다. 선정 건 취소 때 「산출물을 낸 건은 막는다」도 화면에만 있다(D-116 에 적힌 한계)

## 4. 규칙을 바꿀 때마다 — 점검표

- [ ] 이번에 **서버가 새로 읽기 시작한 칸**이 있나? → 그 칸을 회원이 create·update 로 쓸 수 없는지
- [ ] 이번에 **화면 검사를 새로 넣거나 강화**했나? → 같은 조건이 규칙에도 있는지
- [ ] create 규칙이 **칸 목록 없이** 열려 있지 않나? (`keys().hasOnly` 또는 금지 칸 확인)
- [ ] update 에서 본인이 바꿀 수 있는 칸이 `affectedKeys().hasOnly` 로 못 박혀 있나?
- [ ] 서버 경로가 판단에 쓰는 사실을 **회원이 쓴 사본이 아니라 출처 문서**에서 읽나?
- [ ] 주석의 약속과 코드가 같은가?
- [ ] 테스트 계정(`tester`)처럼 **역할별로 문이 다르게 열리는 곳**에서, 그 역할이 아닌 사람이 같은 문을 통과하지 못하나?
- [ ] 바꾼 뒤 `npm run rules` · 배포본에서 **정상 흐름이 막히지 않는지**(제출·재제출·취소·수정) 확인

### 10/7 뒤에 고칠 것 (09-29 Cowork 지시문 · Code 세션 확인)

`firestore.rules` 만. 조건을 **더하기만** 한다 — 정상 흐름(제출·수정·재제출·취소)이 전부 통과하는지 테스트 계정·일반 회원 둘 다로 시험.

1. `support_applications` `allow create` 에 `&& !('sheetSkipped' in request.resource.data)`
2. `support_outputs` `allow create` 에 같은 줄
3. ✅ **D-117 (09-30)** — `support_settlements` `allow create`: 받는 칸 목록(`keys().hasOnly` — `sheetSkipped`·`paidAt` 등 서버·담당자 칸이 목록에 없음) · `status == 'submitted'` · 증빙서류 1~50장 · **자기의 선정된 신청 건**(`get` 으로 신청서 확인) · 번호와 회차가 맞는지(1차 = 신청번호, 2차부터 `신청번호_N` + 1차가 있어야)
4. ✅ **D-117** — 본인 update(반려 뒤 재제출): 5번의 칸 목록에 `sheetSkipped` 가 없어 **바꾸지 못함** + 증빙서류 1~50장.
   ⚠️ update 에는 `!('sheetSkipped' in …)` 를 쓰지 않는다 — 서버가 「시험」 표시를 붙인 테스트 계정 정산의 재제출이 막힌다
5. ✅ **D-117** — (§3 A) 정산 본인 update 를 `affectedKeys().hasOnly([...])` 로 — `resubmitSettlement` 가 쓰는 칸만: `status · bankInfo(지우기) · receipts · reviewNote · submittedAt · updatedAt`
6. 신청서·산출물의 본인 update 는 이미 `affectedKeys().hasOnly` 라 손대지 않는다
7. (§3 G) 1번 줄에 같은 방식으로 `cancelledFromStatus` 도 — `&& !('cancelledFromStatus' in request.resource.data)`.
   본인 취소 조항은 이미 이 칸을 묶고 있어 그대로 둔다. `editCount`·`lastEditedAt` 까지 막을지는 함께 판단
8. (§3 F — **규칙이 아니라 서버 코드**) 신청 동기화는 `generatedPdfPath` 가 `support/applications/{주인 uid}/{신청번호}/`
   아래일 때만, 정산 동기화는 영수증 경로가 `support/settlements/{주인 uid}/` 아래일 때만 내려받는다(아니면 건너뛰고
   `driveSyncError` 에 사유). 공지 첨부 서버의 폴더 확인과 같은 꼴. 규칙 배포 불필요 — 배포본에서 제출·재제출 뒤
   드라이브에 PDF·영수증이 평소대로 올라가는지 확인.
   ✅ **정산 절반은 D-117 (09-30)** — 더 좁게 `support/settlements/{주인 uid}/{정산번호}/` 아래만. 하나라도 벗어나면
