# 에이전트 활용 가이드 — 어떤 세션에 무엇을 맡기나

> **Claude 같은 개발 에이전트에게 이 사이트 일을 맡길 때** 어느 종류의 세션을 열고,
> 무엇을 어떻게 물어보고, 답을 어떻게 믿을지 정리한 문서입니다.
>
> 🔴 **코드를 몰라도 읽을 수 있게 썼습니다.** 에이전트가 파일 이름을 말할 때 그게
> 무엇인지는 `docs\claude 생성 파일 설명서.md` 를 보세요.
>
> 기준일: 2026-09-25 · **10-08 §2 프롬프트를 「이번 일」(개발 세션이 그때 씀) + 「고정 본문」(낡는 값 없음)으로 나눔** ·
> 9/25 후보는 부록으로

---

## 0. 세 줄 요약

1. 세션은 **두 종류**입니다 — **① 구현·운영**(급한 일) **② 유지보수**(미리 조금씩).
   ②는 항상 ①보다 우선순위가 낮습니다.
2. **①과 ②를 같은 시간에 돌려도 되지만**, 둘이 **같은 작업 폴더**를 쓰므로
   「고치기 전에 `git status`, 끝나면 바로 커밋」을 지켜야 섞이지 않습니다.
3. 에이전트는 **그럴듯하게 틀립니다.** 믿는 기준은 §5 에 있습니다.

## 1. 세션 두 종류 — 무엇을 맡기나

| | **① 구현·운영 세션** | **② 유지보수 세션** |
|---|---|---|
| 언제 | 기능이 필요할 때, 문제가 났을 때, 공고를 올려야 할 때 | 급한 일이 없는 시간에 |
| 무엇을 | 새 기능·버그 수정·문서 갱신·공고 준비 | 코드 정리, 구조 개선, 되풀이되는 사고의 원인 제거 |
| 회원에게 영향 | **있어도 된다** (그게 목적) | 🔴 **절대 없어야 한다** |
| 우선순위 | **높음** | **낮음. 언제든 중단** |
| 프롬프트 | 그때의 요청을 그대로 | **§2 의 긴 프롬프트를 붙여넣기** |

**②를 왜 따로 두나** — 사이트를 만드는 것만이 일이 아니고 **고쳐 가며 오래 쓰게 만드는
것까지**가 일입니다. 그런데 급한 일에 밀려 계속 미루게 되므로, 한가한 시간에 조금씩
떼어 놓으려고 세션을 나눕니다. **급한 일이 생기면 ②는 즉시 접습니다.**

### 일을 어느 쪽에 맡길지 — 개발 세션에서 먼저 가른다 (10-08 sunbell)

1. 새 일이 생기면 **①(개발) 세션이 먼저 본다** — 위 표로 **개발 쪽 일인지 유지보수 쪽 일인지** 가른다
2. 유지보수 쪽이면 ① 세션이 **필요한 준비를 먼저 끝낸다** — 상황 설명 · 읽기 전용 확인 · 지금 할 것과 나중에 할 것 나누기
   (§2 프롬프트 안의 위험 등급 A/B/C) · 문구·순서처럼 sunbell 이 정할 것 받기 · 남은 일에 계획 기록 · 문서 커밋(작업 폴더 비우기)
3. 마지막으로 ① 세션이 **②에 그대로 붙여 넣을 프롬프트를 만들어 준다** — §2-1 「이번 일」(지금 상황 · 맡길 일 · 첫 답변)을
   채워 §2-2 고정 본문 **앞에 붙인 한 덩어리**로. sunbell 은 그것을 새 유지보수 세션에 통째로 붙여 넣는다.
   🔵 **프롬프트가 맞는지는 원문(마크다운)을 읽게 해서가 아니라 말로 설명해서 확인받는다**(10-08 sunbell — 사람이 읽기에
   원문은 불편하다). 설명에 담을 것: **무엇을 · 왜 · 하지 않는 것 · sunbell 이 어디서 무엇을 확인하나 · 운영에 닿는 것 · 판단할 것**
4. ② 세션은 그 계획에서 시작한다. 계획이 틀렸다고 보면(등급이 다르다 등) **근거를 대고 되묻는다** — 그대로 믿지 않는다

처음 적용: 10-08 「10/7 뒤 유지보수」 — 데이터 디깅이 11/6 까지 접수 중이라 「지금 / 문구 확정 뒤 / 11/6 뒤」로 나눔(남은 일).

## 2. 유지보수 세션 프롬프트 — 「이번 일」 + 「고정 본문」 (10-08 나눔)

유지보수 세션에 붙여 넣는 글은 **두 부분을 이어 붙인 한 덩어리**입니다.

| 부분 | 무엇 | 누가 |
|---|---|---|
| **위 — 이번 일** (§2-1 양식) | 지금 상황(접수 중인 공고 · 판 번호 · 작업 폴더) · 맡길 일과 계획 위치 · 첫 답변 | **개발 세션이 그때그때 써 준다** |
| **아래 — 고정 본문** (§2-2) | 세션의 위치 · 금지선 · 등급 · 순서 · 규칙 — 늘 같은 것 | 이 가이드 그대로. 고칠 일이 생기면 여기서 고치고 문서 커밋 |

- 개발 세션은 §1 「일을 어느 쪽에 맡길지」의 준비를 끝낸 뒤 **이번 일 + 고정 본문을 한 덩어리로** 만들어 줍니다.
  sunbell 은 그것을 새 유지보수 세션에 **통째로** 붙여 넣으면 됩니다.
- 🔴 **고정 본문에는 날짜·마감·D 번호를 적지 않습니다** — 낡는 값은 모두 이번 일에. (9/25 판은 접수 표 · 「최신 D-103」 ·
  「파트 1부터」가 본문에 박혀 있어 10-08 에 보니 전부 낡아 있었습니다.)
- 9/25 에 찾은 개선 후보는 본문에서 빼 **부록**(맨 끝)으로 옮겼습니다 — 파트 3 이후를 맡길 때 이번 일에서 가리킵니다.

````
## 0. 🔴 이 세션의 위치 — 먼저 이것부터 받아들여라

**이 작업은 우선순위가 낮다.** 사용자의 본업은 기능 구현과 운영이고, 그 작업은
**다른 세션**에서 진행된다. 이 세션은 *"유지보수·개선까지가 내 일이니 미리 조금씩
시작해 두자"* 는 것이다.

그래서:

- **구현 세션이 무언가를 필요로 하면 이 세션은 즉시 물러난다.** 하던 것을 커밋하거나
  되돌려서 **작업 폴더를 깨끗하게 비우고** 기다린다.
- **한 단계는 한 세션 안에 끝나야 한다.** 며칠 걸리는 변경을 시작하지 마라.
  중간 상태로 남겨 두면 구현 세션이 막힌다 — **그건 실패다.**
- 사용자가 *"이건 나중에"* 라고 하면 즉시 접고 기록만 남긴다. 설득하지 마라.

### ⚠️ 두 세션이 같은 작업 폴더를 쓴다

사용자는 다른 세션(cowork 쪽 포함)에서도 같은 폴더를 건드린다. 그래서:

- **파일을 고치기 전에 반드시 `git status`.** 다른 세션의 **미커밋 변경이 있는 파일은
  건드리지 마라** — 이번 일에 「이어받아라」라고 적힌 것만 예외. 그 밖에는 사용자에게 알리고 다른 일로 넘어간다.
- **한 단계 끝나면 바로 커밋해서 트리를 비운다.** 사용자의 다음 세션 첫 작업이
  `git status` 다 — 네가 남긴 미커밋 변경이 그 세션을 혼란시킨다.
- 브랜치를 새로 만들지 마라. `main` 에 작은 커밋으로 쌓는다.

## 1. 🔴 절대 금지선 — 쓰고 있는 사람에게 영향이 가면 안 된다

**사이트는 지금 운영 중이고 실제 회원이 쓰고 있다.** 어느 공고가 접수 중인지, 신청자가 지금 무엇을
하고 있는지는 **이번 일의 「지금 상황」 표**를 본다. 담당자(교수님·운영 담당자)도 공고를 올리고 신청을 처리하는 중이다.

### 매 변경 전에 이 질문을 통과해야 한다

> **이 변경으로 ① 지금 로그인한 회원이나 담당자가 보는 화면이 한 군데라도
> 달라지는가 ② 저장되는 데이터의 모양이 달라지는가 ③ 제출·저장·동기화 경로가
> 달라지는가?**
>
> 하나라도 「그렇다」면 **이번 일에 그 일이 맡겨져 있지 않은 한 하지 않는다.** 기록만 남기고 다음으로 넘어간다.

### 접수 중인 공고가 있으면 손대지 않는 것

- 그 신청자가 쓰는 화면 — 홈 · 프로그램 목록·상세 · **신청서** · 가입 · 마이페이지 · 내 예약 · 1:1 문의 · 산출물
- 담당자 화면 — 특히 `/staff/programs`(공고 수정)와 `/staff`(신청 목록). 실제 업무에 쓰인다
- `firestore.rules` · `storage.rules`
- 구글 시트·드라이브 동기화 (`lib/server/googleSync.ts`)
- 신청서 PDF 생성 (`components/apply/ApplicationSheet.tsx`, `lib/pdf/*`)

**그러면 할 수 있는 게 뭐냐** → §3 의 **A 등급**이다. 겉으로 아무 변화가 없는 것. 그 밖의 등급은
이번 일에 맡겨진 것만.

## 3. 위험 등급 — 모든 변경을 셋 중 하나로 분류해라

| 등급 | 뜻 | 언제 |
|---|---|---|
| **A** | **아무도 알아챌 수 없다.** 화면·데이터·동작이 **완전히 동일**하고 개발자만 차이를 안다 | 접수 중이어도 가능 |
| **B** | 화면이나 담당자 업무가 조금이라도 달라진다 | 그 화면을 쓰는 공고의 **접수가 끝난 뒤** — 또는 이번 일에 맡겨진 것 |
| **C** | 저장 데이터·규칙·시트 열·PDF 가 바뀐다 | **별도 승인 + 접수가 끝난 뒤** |

**A 등급은 「동일함을 증명」해야 A다.** *"같을 것 같다"* 는 A가 아니다.
예: 인라인 유틸리티를 클래스로 바꿀 때는 **두 유틸리티 집합이 글자 그대로 같은지**
확인하고, 프로덕션 CSS(`.next/static/css/*.css`)에서 결과를 비교해라.
개발 모드는 즉석 생성이라 근거가 못 된다.

**A 등급의 예** — 죽은 코드 제거 · 타입 강화(`Record<모든값, …>` 로 빠짐을 컴파일
오류로 만들기) · 값이 동일한 중복 정의 합치기 · 주석·문서 정리 · 렌더 결과가 같은
클래스 치환.

**A 등급이 아닌 것** — 컴포넌트 쪼개기(렌더 트리가 바뀐다) · 여백·색 조정 ·
함수 이름 변경 중 화면 문구에 닿는 것 · 폴더 구조 변경.

파트 3  디자인 토큰과 공용 클래스 tailwind.config.ts · app/globals.css · components/ui/*
파트 4  공용 유틸               lib/firebase/*.ts 의 순수 함수 · 날짜·문자열 포맷
파트 5  담당자 화면             app/staff/**           ← 여기서부터 대개 B
파트 6  회원 화면               app/(홈·apply·mypage) · components/apply/**  ← B
파트 7  서버 동기화·PDF         lib/server/googleSync.ts · PDF 경로   ← C
```

**파트 안에도 B·C 가 섞여 있다.** 등급은 파트가 아니라 **변경마다** 매긴다.

### 한 가지마다 이 순서로

1. **읽는다** — 실제 파일을 읽는다. 추측하지 마라
2. **보고한다** — 「지금 어떻게 되어 있나」 + 무엇을 바꿀지
   (등급 A/B/C · 왜 · 무엇이 같이 흔들리나 · 확인 방법)
3. **사용자가 고른다** — 할지, 지금 할지 미룰지
4. **하나씩 착수한다** — **한 커밋에 한 가지.** 여러 개를 묶지 마라
5. **확인 방법을 알려준다** — `npm run build` 로 잡히는 것인지, 사람이 화면을 봐야
   하는 것인지. 후자면 **무엇을 어디서(로컬/배포본) 보면 되는지** 구체적으로
6. **승인 뒤 커밋·푸시한다**

🔴 **1~2 를 건너뛰고 고치지 마라.** 보여 주고 사용자가 고르게 하는 것이 이 세션의 핵심이다.
````

## 4. 어떻게 물어보면 좋은가

### 파트 보고를 받은 뒤 — 이렇게 고릅니다

에이전트가 후보 목록을 주면 **전부 하라고 하지 마세요.** 다음 셋 중 하나로 답합니다.

```
「A 등급만 하고, B·C 는 남은-일에 적어 두세요」        ← 접수 중에 기본값
「①번만 먼저 하고 결과를 보여 주세요」                ← 처음 몇 번은 이렇게
「③번은 왜 지금 해야 하는지 다시 설명해 주세요」      ← 근거가 약할 때
```

### 잘 듣는 질문 — 실제로 효과가 있었던 것들

| 물어보기 | 왜 효과가 있나 |
|---|---|
| **「당신의 사고과정을 단계별로 설명해 주세요」** | 결론만 받으면 틀린 전제를 못 봅니다. 실제로 이 질문에서 잘못된 전제가 두 번 드러났습니다 |
| **「그게 무엇이고 화면 어디에서 보이는지 알려주세요」** | 파일 이름만 받으면 확인할 수가 없습니다 |
| **「이걸 안 하면 무엇이 고장나나요」** | *"깔끔해진다"* 만 나오면 지금 할 일이 아닙니다 |
| **「되돌리려면 어떻게 하나요」** | 되돌릴 방법이 없는 변경은 받지 않습니다 |
| **「내가 무엇을 어디서 확인하면 되나요」** | 로컬인지 배포본인지, 무엇을 눌러야 하는지를 받아야 검수가 됩니다 |
| **「이게 규칙 파일을 바꾸나요」** | 바뀌면 제가 `npm run rules` 를 직접 돌려야 합니다 |

### 잘 안 듣는 질문

| 이렇게 묻지 마세요 | 무슨 일이 생기나 |
|---|---|
| 「코드 좀 깔끔하게 정리해줘」 | 범위가 없어서 한 번에 수십 파일을 건드립니다 |
| 「제일 좋은 방법으로 해줘」 | 판단을 떠넘긴 것이라, 나중에 왜 그랬는지 아무도 모릅니다 |
| 「이거 괜찮아?」 | 대개 「괜찮다」가 돌아옵니다. **무엇이 틀릴 수 있는지**를 물어야 합니다 |
| 「알아서 다 해줘」 | ②에게는 특히 위험합니다. 승인 단계가 사라집니다 |
