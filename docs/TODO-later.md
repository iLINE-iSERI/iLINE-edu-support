## ⚠️ 어디서 시험할 것인가 — 로컬 vs 배포본

### 먼저 알아야 할 것: **데이터베이스는 하나입니다**

로컬(`localhost:3000`)이든 배포본이든 **같은 Firebase 프로젝트**를 봅니다.

```
localhost:3000  ─┐
                 ├─→  Firebase (iline-edu-support)  ← 하나뿐
배포 주소       ─┘        회원 · 신청서 · 공지 · 파일
```

**즉 로컬에서 한 시험도 진짜 데이터를 만듭니다.** 로컬에서 가입한 계정, 올린
공지, 제출한 신청서가 **배포된 사이트에도 그대로 보입니다.** "로컬이니까
지워도 되겠지"가 아니라, **로컬 시험도 정리 대상**입니다.

반대로 **보안 규칙을 콘솔에 게시하면 로컬에도 즉시 적용**됩니다. 규칙 시험은
로컬에서 해도 결과가 같습니다.

### 기준표

| 무엇을 고쳤나 | 어디서 시험 | 왜 |
|---|---|---|
| 화면·폼·흐름 (버튼, 안내 문구, 유효성 검사) | **로컬이면 충분** | 고치고 바로 확인. 배포 기다릴 이유 없음 |
| 보안 규칙 | **로컬이면 충분** | 규칙은 서버에 하나뿐이라 결과가 같음 |
| **서버 코드** (`lib/server/`, `app/api/`) | **배포본 필수** ⚠️ | 아래 참고 |
| 구글 시트·드라이브 연동 | **배포본에서만 동작** | 연동 값 5개가 Vercel 에만 있음. 로컬은 조용히 건너뜀 |
| **날짜·시각 표시** | **배포본 필수** ⚠️ | 아래 참고 |
| 휴대폰 화면 (D-24) | **배포본** | 실기기가 `localhost` 를 못 봄 |
| 도메인·인증서 | **배포본** | 로컬에 해당 없음 |

### ⚠️ 로컬에서는 절대 안 잡히는 것 두 가지

**① 시간대** — 로컬 PC는 **한국 시간**, Vercel 서버는 **UTC** 입니다.
서버에서 만드는 값(드라이브 파일명, 시트의 신청 일시)은 **로컬에서 시험하면
언제나 맞게 나옵니다.** 09-06 의 9시간 오차가 정확히 이 경우였습니다.

**② 환경변수** — 서비스 계정 키·시트 ID 등은 Vercel 에만 있습니다.
로컬에서는 연동이 **오류 없이 건너뜁니다**(의도한 동작). 그래서 로컬에서
"잘 되네" 하고 넘어가면 배포본에서 처음 실패합니다.

> **한 줄 규칙**: 브라우저 안에서 끝나는 일은 로컬, **서버가 관여하면 배포본.**

## ⚠️ 고친 뒤 반영하는 순서

**Vercel 은 GitHub 에 있는 코드로 배포합니다.** 로컬에서 고친 것은 push 해야 올라갑니다.

1. 로컬에서 확인
2. `git add . && git commit -m "..." && git push`
3. Vercel 자동 재배포 (1~2분)
4. **배포된 주소에서 다시 확인** — 위 표의 '배포본 필수' 항목이 있으면 반드시

*(09-05: push 를 빠뜨려 배포본에만 옛 코드가 남아 신청서 제출이 실패한 적 있음)*

**보안 규칙은 GitHub 과 무관합니다.** 콘솔에 따로 게시해야 하고 push 로는
반영되지 않습니다. **규칙과 코드를 함께 고쳤다면 규칙을 먼저** 올리세요 —
반대로 하면 새 코드가 옛 규칙에 막혀 전부 실패합니다.

> 콘솔에서 `게시` 버튼이 흐리면 **내용이 이미 같다는 뜻**입니다. 정말 반영됐는지는
> 동작으로 확인하세요 (예: 담당자 계정으로 공지 작성이 되는지).

## 🎨 I. UI/UX 개선 · 제주 느낌 디자인 (3순위 · 접수 개시 이후)

### I-2. 제주 느낌 반영 (인트로 + 교원양성지원사업)

- [ ] **인트로 사이트** 디자인 — 🟤H 작업과 함께

      *(인트로가 허브이므로 최소한 인트로↔지원사업은 이어져 보여야 합니다)*

> | 정할 것 | 예시 |

>
> ⚠️ **제주대학교 CI(로고·지정색) 사용 규정**을 먼저 확인해야 합니다.
